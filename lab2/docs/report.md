# Лабораторна робота № 2: Керування доступом на рівні стовпців (Column-Level Privileges) та ролі у PostgreSQL (Supabase)

**Дисципліна:** Бази даних  
**Інфраструктура:** Хмарна платформа Supabase (керований кластер PostgreSQL)  
**Базова роль підключення (Owner):** `postgres`  
**Тестова роль з обмеженими правами:** `column_user`  
**Версія PostgreSQL:** 16+  
**Клієнтське середовище:** Supabase SQL Editor / Web Console  

---

## 1. Мета роботи

1. Дослідити реалізацію рольової моделі керування доступом (Role-Based Access Control, RBAC) у СУБД PostgreSQL.
2. Опанувати створення користувацьких ролей з атрибутом `NOLOGIN`, призначених для групування прав та емуляції прав доступу без відкриття окремих фізичних підключень.
3. Дослідити механізм тимчасового сесійного перемикання контексту виконання (`SET ROLE` / `RESET ROLE`) у хмарному середовищі Supabase.
4. Дослідити ієрархію привілеїв у просторах імен СУБД та підтвердити необхідність привілею `USAGE ON SCHEMA` для доступу до об'єктів усередині схеми.
5. Реалізувати та перевірити дискреційний захист на рівні окремих атрибутів таблиці (Column-Level Access Control) шляхом надання дозволу на зміну стовпця `name` та відсутності дозволу на зміну стовпця `rating`.
6. Дослідити поведінку ядра СУБД при спробі несанкціонованої модифікації стовпця, проаналізувати виняток `ERROR: 42501: permission denied for table students`.
7. Зіставити підходи розмежування доступу: права на рівні таблиць, права на рівні стовпців та технологію Row Level Security (RLS).

## 2. Теоретичні відомості та архітектурний аналіз

### 2.1. Уніфікована рольова модель PostgreSQL (RBAC)

У ранніх версіях реляційних СУБД існував поділ на «користувачів» (user) та «групи» (group). Починаючи з версії PostgreSQL 8.1, ці концепції були об'єднані в єдину сутність — **`ROLE`** (роль):
- Всі ролі реєструються в глобальному системному каталозі кластера `pg_authid` (та системному поданні `pg_roles`).
- Роль може виступати як обліковий запис користувача, як група ролей або як абстрактний профіль безпеки.
- Різниця полягає у встановлених прапорцях (атрибутах) ролі:
  - `LOGIN`: дозволяє ролі ініціювати клієнтське з'єднання та автентифікуватися на сервері. Команда `CREATE USER ...` є синтаксичним еквівалентом команди `CREATE ROLE ... WITH LOGIN`.
  - `NOLOGIN`: забороняє пряму автентифікацію. Такі ролі застосовуються виключно для акумуляції прав або для безпечного делегування повноважень через членство (`GRANT role_name TO user_name`).

```text
                             +-----------------------+
                             |   Системний каталог   |
                             |      pg_authid        |
                             +-----------+-----------+
                                         |
                     +-------------------+-------------------+
                     |                                       |
           rolcanlogin = true                      rolcanlogin = false
           +---------+---------+                   +---------+---------+
           |     Користувач    |                   |       Роль        |
           |      (LOGIN)      |                   |     (NOLOGIN)     |
           | Наприклад:        |                   | Наприклад:        |
           | postgres          |                   | column_user       |
           +---------+---------+                   +---------+---------+
                     |                                       ^
                     |          GRANT column_user            |
                     +---------------------------------------+
                                  (членство в ролі)
```

### 2.2. Механізм перемикання контексту сесії (`SET ROLE` / `RESET ROLE`)

Для перевірки або виконання операцій від імені іншої ролі клієнту не обов'язково розривати TCP-з'єднання і проходити повторну автентифікацію за паролем:
- **`SET ROLE <role_name>`**: змінює ідентифікатор активного користувача (`current_user`) на вказану цільову роль. При цьому системний ідентифікатор первинного з'єднання (`session_user`) залишається незмінним.
- Усі наступні SQL-команди перевіряються ядром PostgreSQL на відповідність привілеям ролі, призначеної через `SET ROLE`.
- **`RESET ROLE`**: миттєво повертає активний контекст до значення `session_user` (у нашому випадку — ролі `postgres`).
- У хмарній платформі Supabase це дозволяє тестувати багатокористувацькі політики безпеки безпосередньо через веб-консоль SQL Editor без реєстрації окремих облікових записів або налаштування нових рядків підключення.

### 2.3. Ієрархія просторів імен та привілей `USAGE ON SCHEMA`

PostgreSQL реалізує дворівневу ієрархію об'єктів усередині бази даних: контейнером для відношень (таблиць, полів, індексів) є **схема** (`schema`).

Для того щоб користувач міг звернутися до таблиці `lab_columns.students`, сервер виконує послідовну перевірку двох рівнів прав:
1. **Перевірка доступу до схеми:** користувач зобов'язаний мати привілей `USAGE` на схему `lab_columns`. Без нього механізм розв'язання імен ядра БД не дозволяє «зайти» в схему (повертається помилка `permission denied for schema`).
2. **Перевірка доступу до таблиці/стовпця:** якщо доступ до схеми відкрито, перевіряються конкретні права (`SELECT`, `INSERT`, `UPDATE`, `DELETE`) на саму таблицю або її атрибути.

### 2.4. Дискреційний захист на рівні окремих стовпців (Column-Level Privileges)

Стандартний механізм `GRANT UPDATE ON table TO role` надає дозвіл на модифікацію будь-якого поля таблиці. Проте у реальних інформаційних системах діє **принцип найменших привілеїв (Principle of Least Privilege, PoLP)**: користувачам має бути доступний лише той мінімум даних, який необхідний для виконання їхніх обов'язків.

PostgreSQL підтримує розмежування прав на рівні окремих атрибутів (стовпців):
```sql
GRANT UPDATE (column_name) ON schema_name.table_name TO role_name;
```

**Відмінність від технології Row Level Security (RLS):**
- **Column-Level Privileges (вертикальна ізоляція):** обмежують доступ до певних стовпців для всіх рядків таблиці (наприклад, дозволено змінювати `name`, але заборонено чіпати `rating`).
- **Row Level Security (горизонтальна ізоляція):** обмежує доступ до певних рядків для всіх або обраних стовпців на основі предикату фільтрації (наприклад, студент бачить тільки свій рядок за `user_id = current_user_id()`).

### 2.5. Еволюція механізму членства ролей у PostgreSQL 16+

У версії PostgreSQL 16 було посилено безпеку делегування ролей:
- До версії 15 включно команда `GRANT role TO user;` автоматично дозволяла користувачу виконувати `SET ROLE role;`.
- Починаючи з PostgreSQL 16, додано явну опцію **`WITH SET TRUE`** (`GRANT role TO user WITH SET TRUE;`). Цей прапорець явно санкціонує право перемикання на дану роль через `SET ROLE`. Якщо цей прапорець вимкнено (`WITH SET FALSE`), користувач отримує привілеї ролі шляхом успадкування (`INHERIT`), але не має права явно перемикати контекст сесії.

### 2.6. Механіка пропозицій `WHERE` та `RETURNING *`

При виконанні команди оновлення:
```sql
UPDATE lab_columns.students SET name = 'Denis' WHERE id = 1 RETURNING *;
```
Ядро PostgreSQL вимагає наявності таких привілеїв:
1. `UPDATE (name)` на таблицю `students` — для зміни цільового стовпця.
2. `SELECT (id)` або загальний `SELECT` на таблицю — для обчислення умови фільтрації рядків `WHERE id = 1`.
3. `SELECT (*)` на всі стовпці таблиці — для повернення повного результуючого рядка за допомогою пропозиції `RETURNING *`.

## 3. Протокол виконання та детальний аналіз логів

Усі наведені результати відповідають фактичному протоколу виконання робіт, зафіксованому у файлі `savings.txt`.

### 3.1. Етап 1: Створення структури таблиці від імені власника (`postgres`)

Від імені адміністратора бази даних `postgres` було створено ізольовану схему `lab_columns`, таблицю `students` та додано тестовий запис про студента.

**Виконані команди:**
```sql
RESET ROLE;
CREATE SCHEMA IF NOT EXISTS lab_columns;

CREATE TABLE IF NOT EXISTS lab_columns.students (
    id INTEGER PRIMARY KEY,
    name TEXT,
    rating INTEGER
);

INSERT INTO lab_columns.students (id, name, rating)
VALUES (1, 'Illia', 87);

SELECT * FROM lab_columns.students;
```

**Фактичний результат виконання (з `savings.txt`):**
```text
| id | name  | rating |
| -- | ----- | ------ |
| 1  | Illia | 87     |
```

*Аналіз:* Запис успішно створено. Роль `postgres` є власником (`table owner`), тому має абсолютні права на читання та запис усіх стовпців.

---

### 3.2. Етап 2: Створення ролі `column_user` та налаштування прав доступу

Створено роль без права входу та призначено їй гранулярні привілеї.

**Виконані команди:**
```sql
RESET ROLE;

-- Створення ролі
CREATE ROLE column_user NOLOGIN;

-- Дозвіл для postgres перемикатися на column_user
GRANT column_user TO postgres WITH SET TRUE;

-- Надання доступу до схеми lab_columns
GRANT USAGE ON SCHEMA lab_columns TO column_user;

-- Надання права читання всіх стовпців
GRANT SELECT ON lab_columns.students TO column_user;

-- Надання права редагування ВИКЛЮЧНО стовпця name
GRANT UPDATE (name) ON lab_columns.students TO column_user;
```

*Аналіз:* Стовпець `rating` не включено до списку дозволених для команди `UPDATE`. Отже, будь-які спроби ролі `column_user` оновити значення рейтингу будуть заблоковані.

---

### 3.3. Етап 3: Перевірка читання від імені `column_user`

Виконано перемикання контексту на `column_user` за допомогою `SET ROLE` та перевірено доступ на читання.

**Виконані команди:**
```sql
SET ROLE column_user;
SELECT current_user, name, rating FROM lab_columns.students;
```

**Фактичний результат виконання (з `savings.txt`):**
```text
| current_user | name  | rating |
| ------------ | ----- | ------ |
| column_user  | Illia | 87     |
```

*Аналіз:* Запит повернув правильні значення. Поле `current_user` підтверджує, що сесія виконує команди під правами `column_user`. Оскільки було видано `GRANT SELECT ON lab_columns.students`, читання обох стовпців (`name` та `rating`) повністю дозволено.

---

### 3.4. Етап 4: Дозволена модифікація стовпця `name`

Перевірено виконання операції `UPDATE` для стовпця, на який було видано явний дозвіл.

**Виконані команди:**
```sql
SET ROLE column_user;
UPDATE lab_columns.students
SET name = 'Denis'
WHERE id = 1
RETURNING *;
```

**Фактичний результат виконання (з `savings.txt`):**
```text
| id | name  | rating |
| -- | ----- | ------ |
| 1  | Denis | 87     |
```

*Аналіз:* Модифікація стовпця `name` пройшла успішно. Значення змінилося з `'Illia'` на `'Denis'`. Пропозиція `RETURNING *` повернула оновлений рядок, оскільки роль має право `SELECT` на всі стовпці.

---

### 3.5. Етап 5: Спроба несанкціонованої модифікації стовпця `rating`

Під роллю `column_user` виконано спробу модифікувати стовпець `rating`, на який дозвіл не надавався.

**Виконана команда:**
```sql
SET ROLE column_user;
UPDATE lab_columns.students
SET rating = 87
WHERE id = 1;
```

**Фактичний результат виконання (з `savings.txt`):**
```text
Error: Failed to run sql query: ERROR: 42501: permission denied for table students
```

*Аналіз:* Ядро СУБД миттєво відхилило операцію та сформувало виняток з кодом `42501` (`insufficient_privilege`). Це доводить надійність та абсолютну ізоляцію дискреційного захисту стовпців у PostgreSQL: без наявності привілею `UPDATE (rating)` транзакція не може бути виконана.

---

### 3.6. Етап 6: Підсумкова перевірка стану таблиці від імені власника

Сесію повернуто до початкової ролі `postgres` через `RESET ROLE` для фіксації фінального стану даних.

**Виконані команди:**
```sql
RESET ROLE;
SELECT current_user, id, name, rating FROM lab_columns.students;
```

**Фактичний результат виконання (з `savings.txt`):**
```text
| current_user | id | name  | rating |
| ------------ | -- | ----- | ------ |
| postgres     | 1  | Denis | 87     |
```

*Аналіз:* Підтверджено коректність виконання роботи:
1. Роль повернулася до `postgres`.
2. Поле `name` зберегло дозволену зміну (`'Denis'`).
3. Поле `rating` залишилося незмінним (`87`), оскільки заборонена операція не вплинула на сховище.

## 5. Відповіді на контрольні питання

### 1. Що таке роль у PostgreSQL?
Уніфікована сутність моделі керування доступом на основі ролей (RBAC). Роль об'єднує властивості користувачів і груп, може володіти об'єктами бази даних (таблицями, схемами) та отримувати або делегувати привілеї.

### 2. Чим відрізняється роль з атрибутом `LOGIN` від `NOLOGIN`?
Роль з атрибутом `LOGIN` є повноцінним користувачем, який може автентифікуватися на сервері за паролем або сертифікатом та ініціювати пряме з'єднання. Роль з `NOLOGIN` не може підключатися безпосередньо; вона використовується як група або шаблон привілеїв, на який інша роль може перемкнутися за допомогою команди `SET ROLE`.

### 3. Для чого призначена команда `SET ROLE`?
Для тимчасової зміни ідентифікатора активного користувача (`current_user`) поточної сесії на вказану цільову роль. Це дозволяє виконувати SQL-запити в межах прав цільової ролі без необхідності повторного відкриття TCP-з'єднання.

### 4. Що робить команда `RESET ROLE`?
Скидає контекст безпеки сесії до початкової ролі автентифікації (`session_user`), від імені якої було відкрито клієнтське підключення (у лабораторній роботі — до ролі `postgres`).

### 5. Що таке привілей на рівні стовпця (Column-Level Privilege)?
Це механізм гранулярного розмежування прав, що дозволяє надавати привілеї (`SELECT`, `INSERT`, `UPDATE`, `REFERENCES`) не на всю реляційну таблицю повністю, а вибірково на окремі її стовпці.

### 6. Який синтаксис використовується для обмеження прав на зміну окремого стовпця?
```sql
GRANT UPDATE (<список_стовпців>) ON <схема>.<таблиця> TO <роль>;
```
Наприклад: `GRANT UPDATE (name) ON lab_columns.students TO column_user;`.

### 7. Чому виникає помилка при спробі змінити `rating` роллю `column_user`?
Оскільки для ролі `column_user` право `UPDATE` було надано виключно для атрибута `name`, спроба оновити `rating` призводить до порушення прав доступу. Диспетчер прав PostgreSQL генерує помилку `ERROR: 42501: permission denied for table students` та відхиляє транзакцію.

### 8. Навіщо потрібен привілей `GRANT USAGE ON SCHEMA`?
Схема виступає обов'язковим простором імен (контейнером). Без привілею `USAGE` користувач не може переглядати вміст схеми або резолвити імена об'єктів усередині неї, навіть якщо на конкретну таблицю в цій схемі йому надано всі права.

### 9. Для чого у PostgreSQL 16 використовується опція `WITH SET TRUE`?
У PostgreSQL 16 запроваджено прапорець `WITH SET TRUE` у команді `GRANT role TO user` для явного надання дозволу перемикатися на цю роль за допомогою команди `SET ROLE`. Це захищає систему від несанкціонованого перемикання контексту користувачами, які отримали роль лише для спадкування прав (`INHERIT`).

### 10. Чому для виконання `UPDATE ... RETURNING *` потрібен привілей `SELECT`?
Пропозиція `RETURNING *` вимагає вибірки та повернення клієнту значень усіх стовпців оновленого рядка. Якщо користувач не має права `SELECT` на стовпці, що повертаються, ядро бази даних блокує виконання запиту, навіть якщо сама дія `UPDATE` для цільових колонок є дозволеною.

### 11. Чи потрібен окремий обліковий запис у Supabase для тестування різних ролей?
Ні. Завдяки механізму `SET ROLE` розробник або адміністратор може повноцінно емулювати поведінку та обмеження будь-яких користувацьких ролей безпосередньо у вікні SQL Editor від імені базової ролі `postgres`.

### 12. Хто є власником (`owner`) таблиці та які права він має за замовчуванням?
Власником таблиці стає роль, яка виконала інструкцію `CREATE TABLE` (у роботі — `postgres`). Власник об'єкта за замовчуванням володіє абсолютними правами на читання, запис, зміну структури (`ALTER TABLE`), призначення привілеїв іншим користувачам (`GRANT`) та видалення таблиці (`DROP TABLE`).

## 6. Висновки

1. **Реалізація дискреційного доступу:** У ході виконання лабораторної роботи було успішно налаштовано дискреційне розмежування доступу на рівні стовпців у реляційній базі даних PostgreSQL під керуванням хмарної платформи Supabase.
2. **Перевірка ізоляції стовпців:** Практично підтверджено ефективність обмеження `GRANT UPDATE (name)`: роль `column_user` успішно змінила значення дозволеного поля `name` з `'Illia'` на `'Denis'`, але отримала системну відмову в доступі (`ERROR: 42501: permission denied`) при спробі модифікації стовпця `rating`.
3. **Ефективність `SET ROLE`:** Доведено зручність використання ролей з прапорцем `NOLOGIN` та сесійних інструкцій `SET ROLE` / `RESET ROLE` для тестування матриці доступу в хмарних середовищах без необхідності генерації додаткових паролів та створення нових мережевих з'єднань.
4. **Ієрархія безпеки:** Підтверджено дворівневу модель захисту просторів імен PostgreSQL, де наявність привілею `USAGE ON SCHEMA` є обов'язковою передумовою для доступу до таблиць усередині схеми.
5. **Дотримання принципу найменших привілеїв:** Застосування прав на рівні окремих стовпців дозволяє мінімізувати площу вразливості системи та захистити критичні бізнес-поля (наприклад, фінансові показники, системні оцінки чи статуси) від несанкціонованої модифікації прикладними користувачами.
