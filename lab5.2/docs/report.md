## 2. Теоретичні відомості та архітектурний аналіз

### 2.1. Ізоляція схеми та ризики мутації `search_path` (Anti-pattern)

У реляційній СУБД PostgreSQL схеми (`schemas`) виступають логічними просторами імен усередині однієї бази даних. Параметр конфігурації `search_path` визначає черговість перегляду схем, коли користувач звертається до таблиці за некваліфікованим ім'ям (наприклад, `SELECT * FROM sensors;` замість `SELECT * FROM lab5.sensors;`).

#### Чому `SET search_path` є поганою інженерною практикою (Bad Practice):
1. **Сесійна волатильність:** Команда `SET search_path` діє суто в межах поточного з'єднання. Під час відкриття нової вкладки в psql, рестарту застосунку, використання пулу з'єднань (PgBouncer, HikariCP) або перепідключення параметр скидається до стандартного (`"$user", public`). Усі запити без префікса негайно зазнають збою з помилкою `42P01: relation does not exist`.
2. **Вразливість безпеки (Search-path Hijacking):** Якщо недобросовісний користувач або сторонній скрипт створить однойменну функцію, оператор чи таблицю в загальнодоступній схемі `public`, ядро PostgreSQL виконає підмінений об'єкт замість цільового, оскільки `public` зазвичай входить до шляху пошуку.
3. **Невизначеність міграцій та аудиту:** При аналізі логів і міграційних скриптів неможливо детерміновано встановити, до якої конкретно таблиці звертається запит, якщо схема не зафіксована явно.

**Рекомендований стандарт:** Повна відмова від маніпуляцій із `search_path`. Абсолютно всі об'єкти в DDL та DML запитах повинні явно кваліфікуватися: `lab5.sensors`, `lab5.readings`, `lab5.sensor_settings`.

### 2.2. Регістронезалежний пошук за шаблоном: `ILIKE` проти `LIKE`

Стандартний SQL-оператор `LIKE` здійснює суворе бінарне або посимвольне порівняння з урахуванням регістру (`case-sensitive`). У багатьох прикладних системах (наприклад, інвентаризація обладнання) маркування може вводитися як у верхньому, так і в нижньому регістрі (`esp-01` проти `ESP-01`):

- `WHERE code LIKE 'esp%'` поверне `false` для `'ESP-01'`.
- Для регістронезалежного пошуку в стандартному SQL доводиться використовувати важкі обгортки `LOWER(code) LIKE 'esp%'`, які без створення функціонального індексу призводять до повного сканування таблиці (`Seq Scan`).
- PostgreSQL надає вбудоване оптимізоване розширення **`ILIKE`**, яке виконує пошук без урахування регістру згідно з активною локаллю сервера.
- Спеціальні метасимволи шаблону:
  - `%` — будь-яка послідовність із нуля або більше символів.
  - `_` — рівно один довільний символ.

### 2.3. Агрегатні функції та семантика `NULL`

Агрегатні функції обробляють набір рядків і обчислюють єдине зведене значення для кожної групи:

```text
               Таблиця readings (esp-02):
       ┌──────┬──────────────┬─────────────┐
       │  id  │  sensor_id   │ temperature │
       ├──────┼──────────────┼─────────────┤
       │  4   │      2       │    30.00    │
       │  5   │      2       │    32.00    │
       │  6   │      2       │    NULL     │ ◄── Значення відсутнє
       └──────┴──────────────┴─────────────┘
                      │
         ┌────────────┴────────────┐
         ▼                         ▼
     COUNT(*)              COUNT(temperature)
   Рахує рядки             Ігнорує NULL
   Результат: 3            Результат: 2
```

1. **`COUNT(*)`:** Обчислює фізичну кількість знайдених записів у групі незалежно від того, чи містять стовпці значення `NULL`.
2. **`COUNT(column)`:** Рахує виключно ті рядки, де значення зазначеного стовпця строго `IS NOT NULL`.
3. **Обчислювальні агрегати (`AVG`, `SUM`, `MIN`, `MAX`):** Повністю ігнорують рядки з `NULL`. Середнє арифметичне обчислюється як ділення суми відомих значень на кількість відомих значень:
   $$\text{avg\_temp} = \frac{30.00 + 32.00}{2} = 31.00$$
   Якщо всі значення стовпця в групі рівні `NULL`, агрегатна функція повертає `NULL` (а не 0).

---

### 2.4. Диференційована агрегація за допомогою клаузи `FILTER (WHERE ...)`

У класичному SQL для паралельного розрахунку агрегатів за різними критеріями використовували конструкцію `CASE`:
```sql
COUNT(CASE WHEN is_valid THEN 1 END) AS valid_cnt
```
Стандарт SQL:2003 представив спеціальну пропозицію **`FILTER`**, повністю реалізовану в PostgreSQL:
```sql
COUNT(*) FILTER (WHERE is_valid) AS valid
```
- **Переваги над `CASE`:** Читабельний декларативний синтаксис, пряма інтеграція в рушій агрегації ядра PostgreSQL, можливість застосування до будь-яких агрегатних функцій (`AVG(temperature) FILTER (WHERE is_valid)`).
- Дозволяє за один прохід таблицею обчислити паралельні метрики (`total`, `valid`, `invalid`, `hot`) без створення підвибірок чи множинних з'єднань.

---

### 2.5. Фільтрація груп: семантика `HAVING` проти `WHERE`

- **`WHERE`:** Виконується **до** групування. Відсікає окремі вихідні кортежі. Не може містити виклики агрегатних функцій, оскільки на цьому етапі групи ще не сформовані.
- **`HAVING`:** Виконується **після** групування (`GROUP BY`) та обчислення значень агрегатних функцій. Фільтрує готові групи (наприклад, `HAVING AVG(temperature) > 20`).

---

### 2.6. Отримання останнього стану через `DISTINCT ON` та узгодження з `ORDER BY`

Конструкція `DISTINCT ON (expr1, ...)` — специфічне високоефективне розширення PostgreSQL, що дозволяє усунути дублікати та зберегти рівно один рядок для кожної унікальної групи виразів.

**Синтаксичне правило детермінованості:**
1. Перший стовпець/вираз у пропозиції `ORDER BY` **зобов'язаний точно відповідати** списку стовпців у `DISTINCT ON (...)`.
2. Подальші вирази в `ORDER BY` задають критерій вибору єдиного рядка, який буде залишено.
Наприклад, для вибірки найостаннішого достовірного вимірювання датчика:
```sql
SELECT DISTINCT ON (sensor_id)
    sensor_id, id, measured_at, temperature
FROM lab5.readings
WHERE is_valid AND temperature IS NOT NULL
ORDER BY sensor_id, measured_at DESC, id DESC;
```
Сортування за `sensor_id` групує записи за сенсорами, `measured_at DESC` піднімає найновіший запис на початок, а `id DESC` гарантує однозначний вибір кортежу у випадку збігу часових міток.

### 2.7. Атомарний зворотний зв'язок операцій DML: конструкція `RETURNING`

Пропозиція `RETURNING` дозволяє командам `INSERT`, `UPDATE` та `DELETE` повертати результуючий набір кортежів подібно до `SELECT`:
- **Усунення стану гонитви (Race Condition):** Забезпечує читання зміненого рядка в момент виконання без ризику, що інша сесія змінить його між транзакціями.
- **Отримання згенерованих сурогатних ключів:** Після виконання `INSERT` повертає присвоєний `id` (`RETURNING id`), усуваючи необхідність викликати `currval()` чи робити повторний пошук.
- **Зниження навантаження на мережу:** Об'єднує команду мутації та запит верифікації в один мережевий пакет (one round-trip).

---

### 2.8. Модифікація та очищення пов'язаних даних: `UPDATE ... FROM` та `DELETE ... USING`

Під час синхронізації або очищення нормалізованих даних стандартний підхід із підзапитами (`WHERE id IN (SELECT ...)`) є громіздким та неефективним. PostgreSQL надає розширення з прямим з'єднанням:
- **`UPDATE target AS t SET col = src.val FROM source AS src WHERE t.id = src.target_id;`**
- **`DELETE FROM target AS t USING source AS src WHERE t.id = src.target_id AND src.condition;`**

> [!CAUTION]
> **Небезпека декартового добутку (Cartesian Product):**
> Якщо розробник забуде вказати умову з'єднання у `WHERE` (наприклад, пропустить `r.sensor_id = s.id`), рушій СУБД утворить повне декартове з'єднання. У результаті кожен рядок оновиться значенням випадкового кортежу джерела або таблиця очиститься повністю!

---

### 2.9. Стратегії вирішення колізій: `ON CONFLICT` проти `MERGE`

| Критерій | `INSERT ... ON CONFLICT` (Upsert) | `MERGE INTO ... USING` (ANSI SQL) |
| :--- | :--- | :--- |
| **Підтримка версіями** | Доступний з PostgreSQL 9.5 | Впроваджений у PostgreSQL 15+ |
| **Обов'язкова вимога** | Потребує унікального індексу або обмеження (`UNIQUE`/`PK`) | Може працювати з будь-якою довільною умовою з'єднання `ON` |
| **Джерело значень** | Працює з рядком, що вставляється, через `EXCLUDED` | Працює з повноцінною таблицею-джерелом `USING source` |
| **Гнучкість дій** | Лише `DO NOTHING` або `DO UPDATE` над рядком, що конфліктує | Підтримує кілька гілок `WHEN MATCHED THEN UPDATE/DELETE`, `WHEN NOT MATCHED THEN INSERT` |
| **Основне застосування** | Точкові ідемпотентні вставки одиночних об'єктів у високонавантажених API | Пакетні ETL-процедури, синхронізація довідників та імпорт |

---

### 2.10. Корельовані табличні вирази через `LATERAL`

Ключове слово `LATERAL` перед підзапитом у пропозиції `FROM` або `JOIN` змінює область видимості змінних: воно дозволяє підзапиту посилатися на стовпці таблиць, які перераховані ліворуч від нього в запиті.

```text
Таблиця sensors (s)             Підзапит LATERAL (для кожного s.id)
┌────────┬────────┐               ┌──────────────────────────────────────────────┐
│  id    │  code  │ ────────────► │ SELECT id, temperature FROM readings r       │
├────────┼────────┤  Передає      │ WHERE r.sensor_id = s.id                     │
│   1    │ esp-01 │  s.id = 1     │ ORDER BY measured_at DESC LIMIT 2            │
│   2    │ esp-02 │               └──────────────────────────────────────────────┘
│   4    │ esp-04 │ (повертає до 2 записів персонально для КОЖНОГО сенсора)
└────────┴────────┘
```

- Підзапит `LATERAL` виконується ітеративно для кожного рядка зовнішнього джерела (механізм `for-each`).
- Дозволяє використовувати персональне обмеження **`LIMIT N`** всередині групи (вирішення задачі «Top-N рядків у кожній категорії»).
- Використання **`LEFT JOIN LATERAL ... ON true`** гарантує, що батьківський рядок (наприклад, датчик `esp-04`, що взагалі не має вимірювань) не випаде з результуючої вибірки, повертаючи поля підзапиту як `NULL`.

### 2.11. Зведена архітектурна таблиця розширених конструкцій SQL

| Конструкція | Синтаксичний блок | Основне призначення | Практичний ефект у проєкті |
| :--- | :--- | :--- | :--- |
| **`ILIKE`** | `WHERE col ILIKE '...'` | Пошук рядків без урахування регістру | Відбір датчиків `'ESP-%'` та коду `'датчик'` |
| **`FILTER`** | `AGG(...) FILTER (WHERE ...)` | Ізольована умовна агрегація | Одночасний підрахунок valid/invalid/hot вимірювань |
| **`HAVING`** | `GROUP BY col HAVING ...` | Фільтрація агрегованих груп | Відбір сенсорів із середньою температурою > 20 °C |
| **`DISTINCT ON`** | `SELECT DISTINCT ON (...)` | Відбір єдиного рядка на групу | Знаходження останнього достовірного показу сенсора |
| **`RETURNING`** | `INSERT/UPDATE/DELETE ... RETURNING` | Миттєве повернення змінених даних | Отримання нового порогу alert_limit без `SELECT` |
| **`UPDATE ... FROM`** | `UPDATE s SET ... FROM cfg WHERE ...` | Пакетне оновлення з іншої таблиці | Синхронізація лімітів із таблиці `sensor_settings` |
| **`DELETE ... USING`**| `DELETE FROM r USING s WHERE ...` | Каскадне очищення за таблицею | Видалення вимірювань для неактивних датчиків |
| **`ON CONFLICT`** | `INSERT ... ON CONFLICT (...) DO UPDATE` | Атомарний Upsert унікальних ключів | Оновлення параметрів повторного датчика `esp-02` |
| **`MERGE`** | `MERGE INTO s USING i ON ...` | Комплексна синхронізація таблиць | Оновлення наявних та додавання нових датчиків |
| **`LATERAL`** | `LEFT JOIN LATERAL (...) ON true` | Корельований підзапит із `LIMIT` | Вибірка N останніх вимірювань на кожен датчик |

### 3.2. Створення таблиць та вторинних індексів

Створено таблиці `sensors`, `readings`, `sensor_settings`, `sensor_import` та вторинні B-tree індекси:

```sql
CREATE SCHEMA IF NOT EXISTS lab5;

CREATE TABLE IF NOT EXISTS lab5.sensors (
    id          integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    code        varchar(20)  NOT NULL UNIQUE,
    name        varchar(100) NOT NULL,
    room        varchar(20),
    active      boolean      NOT NULL DEFAULT true,
    alert_limit numeric(5,2)          DEFAULT 30
);

CREATE TABLE IF NOT EXISTS lab5.readings (
    id          integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    sensor_id   integer   NOT NULL REFERENCES lab5.sensors(id),
    measured_at timestamp NOT NULL,
    temperature numeric(5,2),
    is_valid    boolean   NOT NULL DEFAULT true
);

CREATE INDEX IF NOT EXISTS idx_readings_sensor_id
    ON lab5.readings(sensor_id);

CREATE INDEX IF NOT EXISTS idx_readings_measured_at
    ON lab5.readings(measured_at);

CREATE TABLE IF NOT EXISTS lab5.sensor_settings (
    sensor_id   integer PRIMARY KEY REFERENCES lab5.sensors(id),
    alert_limit numeric(5,2) NOT NULL
);

CREATE TABLE IF NOT EXISTS lab5.sensor_import (
    code varchar(20),
```

### 3.11. Підсумкове комплексне завдання моніторингу активних датчиків

Запит формує єдиний аналітичний звіт для активних сенсорів із префіксом `ESP-`: виводить останнє валідне значення, загальну кількість та кількість відхилених показів:

```sql
SELECT
    s.code,
    latest.temperature AS last_valid,
    stats.total,
    stats.invalid
FROM lab5.sensors AS s
LEFT JOIN LATERAL (
    SELECT r.temperature
    FROM lab5.readings AS r
    WHERE r.sensor_id = s.id
      AND r.is_valid
      AND r.temperature IS NOT NULL
    ORDER BY r.measured_at DESC, r.id DESC
    LIMIT 1
) AS latest ON true
CROSS JOIN LATERAL (
    SELECT
        COUNT(*)                               AS total,
        COUNT(*) FILTER (WHERE NOT r.is_valid) AS invalid
    FROM lab5.readings AS r
    WHERE r.sensor_id = s.id
) AS stats
WHERE s.active
  AND s.code ILIKE 'ESP-%'
ORDER BY s.code;
```

Фактичний результат виконання:

```text

--------+------------+-------+---------
 esp-01 |      24.00 |     3 |       1
 esp-02 |      32.00 |     3 |       1
 esp-04 |            |     0 |       0
(3 rows)
```

Результат повністю збігається з еталонною Таблицею 3 лабораторної роботи.

## 4. Обов'язкові пункти для подання у звіті (Вимоги до звіту)

1. **DDL створення схеми `lab5` та об'єктів (Розділ 1):** Створено ізольовану схему `lab5`, таблиці `sensors`, `readings`, `sensor_settings`, `sensor_import` та вторинні B-tree індекси. Усі об'єкти детерміновано верифіковано в `pg_tables`.
2. **Наповнення первинними даними (Розділ 2):** Сформовано набір показів за допомогою безпечного зв'язування з кодом датчика через конструкцію `JOIN (VALUES ...)`. Зафіксовано наявність пропусків (`NULL`) для `esp-02`, однакових часових міток для `esp-01` та відсутність вимірювань для `esp-04`.
3. **Регістронезалежний пошук `ILIKE` (Розділ 3):** Реалізовано вибірку за шаблоном `'ESP-%'` та знайдено 4 датчики за коренем назви `'датчик'` незалежно від регістру літер.
4. **Агрегатні обчислення та поведінка `NULL` (Розділ 4):** Доведено, що `COUNT(*)` повертає 3 для сенсора 2, а `COUNT(temperature)` — 2 через наявність `NULL`. За допомогою клаузи `HAVING AVG(temperature) > 20` відфільтровано групи після агрегації (залишено датчики 1 та 2).
5. **Диференційована агрегація `FILTER` (Розділ 5):** В одному проході обчислено стовпці `total`, `valid`, `invalid`, `hot` та комбінований показник `hot_valid` (Таблиця 2).
6. **Дедуплікація та відбір через `DISTINCT ON` (Розділ 6):** Отримано останній валідний показ для кожного датчика із вирішенням колізії часу за `id DESC`, а також порівняно поведінку з вибіркою останнього запису без фільтрації за валідністю.

8. **Модифікація зв'язаних даних `UPDATE ... FROM` (Розділ 8):** Оновлено пороги сенсорів безпосередньо з таблиці `sensor_settings` за один прохід СУБД.
9. **Очищення даних `DELETE ... USING` (Розділ 9):** Видалено 2 покази неактивного сенсора `esp-03` із явним контролем зв'язку для запобігання декартовому добутку.

## 5. Відповіді на контрольні запитання

### 1. Чим `ILIKE` відрізняється від `LIKE`?
**Відповідь:**  
Оператор `LIKE` чутливий до регістру символів (`case-sensitive`), тому шаблони `'esp%'` та `'ESP%'` повернуть зовсім різні результати. Оператор `ILIKE` — це розширення PostgreSQL, що виконує пошук за шаблоном без урахування регістру символів (`case-insensitive`) відповідно до правил активної локалі сервера.

### 2. Чим `COUNT(*)` відрізняється від `COUNT(temperature)`?
**Відповідь:**  
`COUNT(*)` підраховує загальну фізичну кількість кортежів у групі або таблиці незалежно від того, чи заповнені їхні стовпці значеннями або містять `NULL`. Натомість `COUNT(temperature)` перевіряє значення конкретного стовпця та ігнорує всі рядки, де значення дорівнює `NULL`, підраховуючи лише фактично відомі величини.

### 3. Для чого потрібен `HAVING`?
**Відповідь:**  
`HAVING` призначений для фільтрації зведених груп **після** завершення операцій групування (`GROUP BY`) та розрахунку агрегатних функцій. Клауза `WHERE` відсікає окремі вихідні рядки **до** групування і принципово не може містити агрегатні вирази.

### 4. Чим `FILTER` відрізняється від `WHERE`?
**Відповідь:**  
Клауза `WHERE` фільтрує вхідні кортежі для всього SQL-запиту в цілому, виключаючи невідповідні рядки з подальшої обробки всіма стовпцями. Клауза `FILTER (WHERE ...)` застосовується локально до окремої конкретної агрегатної функції, дозволяючи обчислювати паралельні агрегати з різними критеріями в одному запиті без розділення на підзапити.

### 5. Що робить `DISTINCT ON`?
**Відповідь:**  
Конструкція `DISTINCT ON (expr1, ...)` видаляє дублікати за вказаним набором виразів і повертає рівно один (найперший згідно з встановленим сортуванням) рядок для кожної унікальної групи значень.

### 6. Яка роль `ORDER BY` у `DISTINCT ON`?
**Відповідь:**  
У конструкції `DISTINCT ON` пропозиція `ORDER BY` виконує дві критичні ролі:
1. Перший елемент `ORDER BY` обов'язково має збігатися зі списком виразів у дужках `DISTINCT ON`, забезпечуючи попереднє впорядкування записів за групами.
2. Подальші стовпці у `ORDER BY` детермінують, який саме кортеж опиниться першим у групі і буде збережений у результуючій вибірці (наприклад, `measured_at DESC, id DESC` залишає найновіший запис).

### 7. Навіщо потрібен `RETURNING`?
**Відповідь:**  
`RETURNING` дозволяє командам модифікації даних (`INSERT`, `UPDATE`, `DELETE`) повертати додані, оновлені або видалені рядки клієнту без необхідності відправки наступного запиту `SELECT`. Це захищає від станів гонитви у багатокористувацькому середовищі, повертає згенеровані значення лічильників `IDENTITY` та оптимізує мережеву взаємодію.

### 8. Яка роль `FROM` в `UPDATE ... FROM`?
**Відповідь:**  
Клауза `FROM` вказує сторонню таблицю або підзапит, що слугує джерелом нових даних для оновлення. Поля цієї таблиці використовуються у виразі `SET target.col = source.val`, а правило зіставлення рядків задається у секції `WHERE`.

### 9. Яка роль `USING` в `DELETE ... USING`?
**Відповідь:**  
Ключове слово `USING` дозволяє підключити додаткову таблицю безпосередньо до оператора видалення, задаючи умову фільтрації видаляємих рядків на основі зв'язку з іншою сутністю без використання вкладених підзапитів.

### 10. Що таке `EXCLUDED`?
**Відповідь:**  
`EXCLUDED` — це спеціальна віртуальна псевдотаблиця, що існує в контексті оператора `INSERT ... ON CONFLICT DO UPDATE`. Вона містить значення того рядка, який початково передавався оператором `INSERT`, що дозволяє легко оновити поточний запис новими значеннями: `SET name = EXCLUDED.name`.

### 11. Чим `MERGE` відрізняється від `ON CONFLICT`?
**Відповідь:**  
- `ON CONFLICT` — це специфічне розширення PostgreSQL, що обробляє виключно помилки порушення унікальних індексів або первинних ключів у межах команди `INSERT`.
- `MERGE` — стандартний оператор ANSI SQL (PostgreSQL 15+), що виконує комплексне злиття двох джерел за довільною умовою з'єднання (`ON`), підтримуючи водночас множинні розгалуження `WHEN MATCHED THEN UPDATE/DELETE` та `WHEN NOT MATCHED THEN INSERT`.

### 12. Що дає `LATERAL`?
**Відповідь:**  
Ключове слово `LATERAL` надає підзапиту можливість посилатися на стовпці таблиць, розміщених ліворуч від нього в блоці `FROM/JOIN`. Це реалізує логіку «for-each», виконуючи підзапит окремо для кожного рядка зовнішньої таблиці.

### 13. Як працює `LIMIT` у `LATERAL`?
**Відповідь:**  
На відміну від звичайного `LIMIT`, який обмежує розмір усього глобального результуючого набору, `LIMIT` у підзапиті `LATERAL` спрацьовує локально для кожного окремого рядка зовнішнього джерела, дозволяючи відбирати Top-N пов'язаних записів для кожної батьківської сутності.

### 14. Чим `NULL` відрізняється від відсутності рядка?
**Відповідь:**  
- `NULL` позначає, що фізичний кортеж у реляційній таблиці існує, але значення конкретного поля є невизначеним, невідомим або порожнім (наприклад, датчик передав пакет, але сенсор зламаний).
- Відсутність рядка означає, що в таблиці немає жодного запису, який відповідав би критеріям запиту (наприклад, датчик `esp-04` ще жодного разу не виходив на зв'язок).

## 6. Висновки

1. **Опановано архітектурні практики організації просторів імен у PostgreSQL:** Досліджено ризики використання параметра сесії `search_path` (сесійна волатильність, ризик підміни об'єктів search-path hijacking та помилки `42P01`) і практично впроваджено обов'язкову явну двокомпонентну кваліфікацію всіх сутностей назвою схеми `lab5.sensors`, `lab5.readings`.
2. **Засвоєно практичні прийоми регістронезалежного пошуку:** Підтверджено переваги спеціалізованого оператора `ILIKE` для гнучкого зіставлення рядків без необхідності виклику ресурсомістких функцій приведення регістру `LOWER()`.
3. **Досліджено поведінку агрегації за наявності невизначених значень:** Практично верифіковано фундаментальну різницю між підрахунком фізичних рядків `COUNT(*)` та непорожніх значень `COUNT(column)`, а також автоматичне виключення `NULL` із розрахунку середнього значення функцією `AVG()`.
4. **Впроваджено високопродуктивну диференційовану агрегацію через `FILTER`:** Доведено ефективність стандарту `FILTER (WHERE ...)` для розрахунку складних паралельних статистичних метрик (`valid`, `invalid`, `hot`, `hot_valid`) в один прохід без використання вкладених підзапитів або громіздких виразів `CASE`.
5. **Опановано механізм отримання актуальних станів через `DISTINCT ON`:** Досліджено правила узгодження сортування в `ORDER BY` для детермінованого відбору останніх достовірних вимірювань датчиків із розв'язанням часових колізій.
6. **Досліджено інструменти атомарної модифікації та вирішення конфліктів:** Опановано конструкцію `RETURNING` для отримання результатів DML-операцій без повторного читання, конструкції `UPDATE ... FROM` та `DELETE ... USING` для зв'язаних операцій із контролем декартового добутку, а також порівняно механіку точкового `ON CONFLICT` (Upsert з `EXCLUDED`) та універсального оператора `MERGE`.
7. **Реалізовано аналітику типу Top-N per Group на базі `LATERAL`:** Застосовано корельовані підзапити `LEFT JOIN LATERAL` та `CROSS JOIN LATERAL` для формування підсумкового комплексного звіту моніторингу активних датчиків температури, забезпечивши збереження сенсорів без вимірювань та ізольоване застосування `LIMIT` до кожної групи.
