## 2. Архітектура шарів даних (`staging` vs `core`)

У проєкті використано підхід із двома окремими схемами:

1. **`staging` (Шар завантаження / сирих даних):**
   * Таблиця `staging.raw_measurement` містить колонки виключно типу `TEXT` (`sensor_code`, `measured_at`, `value_text`).
   * **Обґрунтування:** На етапі імпорту файлів (CSV, JSON тощо) можливі помилки у форматах дати, кому замість крапки у дробових числах або пропущені значення. Збереження у форматі `TEXT` гарантує, що процес пакетного імпорту не буде перервано помилкою приведення типів (`type casting`).

2. **`core` (Шар бізнес-сутностей / доменної моделі):**
   * Таблиця `core.device`: батьківська таблиця пристроїв із сурогатним автоінкрементним первинним ключем `device_id` (`GENERATED ALWAYS AS IDENTITY`).
   * Таблиця `core.sensor`: таблиця сенсорів із зовнішнім ключем `device_id`, що посилається на `core.device(device_id)` з умовою `ON DELETE CASCADE`. Сенсор має унікальний бізнес-код `sensor_code`, назву фізичної величини `quantity` та одиницю вимірювання `unit_symbol`.

## 4. Аналіз системних каталогів та OID

### 4.1. Що таке OID (Object Identifier)?
В PostgreSQL кожен об'єкт бази даних (база, схема, таблиця, тип даних, індекс) має свій внутрішній унікальний 32-бітний числовий ідентифікатор — **OID**.

За результатами запитів до системних каталогів було з'ясовано:
* База даних `lab_measurements` має `oid = 16389` (у каталозі `pg_database`).
* Таблиця `core.device` має `table_oid = 16393` (у каталозі `pg_class`).
* Таблиця `core.sensor` має `table_oid = 16401` (у каталозі `pg_class`).
* Таблиця `staging.raw_measurement` має `table_oid = 16418` (у каталозі `pg_class`).

Зв'язок між таблицею та її схемою здійснюється через поле `pg_class.relnamespace`, яке дорівнює `pg_namespace.oid`.

### 4.2. Порівняння: `information_schema.columns` проти `\d core.sensor`

Під час виконання лабораторної роботи було виконано вибірку стовпців таблиці `core.sensor` двома способами:

| Характеристика | `information_schema.columns` | Команда `psql` `\d core.sensor` |
| :--- | :--- | :--- |
| **Рівень стандартизації** | Стандарт ANSI SQL-92 / ISO. Є крос-платформним інтерфейсом (підтримується у PostgreSQL, MySQL, SQL Server тощо). | Специфічна внутрішня команда клієнта `psql`. |
| **Формат виводу** | Стандартний реляційний набір рядків і стовпців. Ідеально підходить для програмної обробки (Python, Java, ETL-скрипти). | Людиночитаний текстовий звіт (картка таблиці). |
| **Повнота інформації** | Описує лише колонки та їхні базові типи даних. Обмеження цілісності (PK, FK, CHECK) винесені в окремі представлення `table_constraints`. | Агрегує всю інформацію в одному місці: назви колонок, типи, обмеження `NOT NULL`, значення за замовчуванням, індекси (`Indexes`) та зовнішні ключі (`Foreign-key constraints`). |

## 5. Імпорт файлу та тестування `\copy`

Створено файл `data/measurements.csv`, що містить 4 рядки показників сенсора `CPU_Mhz_001`:
```csv
sensor_code,measured_at,value_text
CPU_Mhz_001,2026-09-03 10:00:00,22.5
CPU_Mhz_001,2026-09-03 10:05:00,22.7
CPU_Mhz_001,2026-09-03 10:10:00,23.1
CPU_Mhz_001,2026-09-03 10:15:00,22.9
```

Виконано клієнтський імпорт:
```text
\copy staging.raw_measurement FROM './data/measurements.csv' WITH (FORMAT csv, HEADER true);
```

### Чому `\copy`, а не `COPY`?
* `COPY` є серверною командою SQL. Вона вимагає доступу до файлу на файловій системі сервера PostgreSQL та привілеїв суперкористувача.
* `\copy` виконується на боці клієнтської утиліти `psql`. Вона зчитує локальний файл на машині клієнта і передає дані потоком через стандартний мережевий протокол PostgreSQL, тому не потребує прав суперкористувача.

### Перевірка:
Запит `SELECT COUNT(*) FROM staging.raw_measurement;` повернув значення `4`, що повністю відповідає очікуваному результату.
