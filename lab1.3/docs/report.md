## 2. Теоретичні відомості та архітектурний аналіз

### 2.1. Клієнт-серверна модель у хмарному середовищі (Supabase)

Класична схема розробки передбачає встановлення сервера СУБД безпосередньо на робочу станцію розробника (`localhost`). У цій лабораторній роботі застосовано сучасну розподілену парадигму:

```text
+-------------------------------------------------------------+
|                      Комп'ютер студента                     |
|  +-------------------------------------------------------+  |
|  |             Клієнтська програма на Python             |  |
|  |            (db_connections.py / db_creations.py)      |  |
|  +---------------------------+---------------------------+  |
|                              |                              |
|  +---------------------------v---------------------------+  |
|  |           Драйвер протоколу PostgreSQL (psycopg)      |  |
|  +---------------------------+---------------------------+  |
+------------------------------|------------------------------+
                               |
                               | Мережа Internet (Захищений канал TLS/SSL)
                               | Порт 5432 (Shared / Session Pooler)
                               v
+-------------------------------------------------------------+
|                     Хмара Supabase (AWS)                    |
|  +-------------------------------------------------------+  |
|  |               Connection Pooler (PgBouncer)           |  |
|  |           (aws-0-[region].pooler.supabase.com)        |  |
|  +---------------------------+---------------------------+  |
|                              |                              |
|  +---------------------------v---------------------------+  |
|  |                  Сервер PostgreSQL 17.6               |  |
|  |   - База: postgres        - PID процесу: 116187       |  |
|  |   - Каталоги: pg_catalog  - Метадані: information_schema |  |
|  +-------------------------------------------------------+  |
+-------------------------------------------------------------+
```

#### Особливості архітектури:
- **Відсутність локального сервера:** На комп'ютері розробника функціонує лише клієнтський Python-код. Сервер працює у високодоступному хмарному середовищі.
- **Роль Connection Pooler (Пулера з'єднань):** Безкоштовний рівень інфраструктури Supabase надає прямі адреси (`db.[ref].supabase.co`) лише за протоколом IPv6. Для забезпечення доступності з мереж, що працюють виключно по IPv4, використовується шлюз пулера (**Shared/Session Pooler** на порті 5432 або 6543), який має маршрутизовану IPv4 адресу.
- **Ідентифікація користувача:** При роботі через пулер ім'я користувача складається з ролі та ідентифікатора проєкту: `postgres.[project-ref]`.

### 2.2. Ієрархія сутностей та призначення схем `core` і `staging`

Логічна ієрархія об'єктів у виконаній роботі має вигляд:

```text
PostgreSQL Instance
│
└── Database: postgres
    ├── Schema: core
    │   ├── Table: device
    │   └── Table: sensor (FK -> device)
    │
    └── Schema: staging
        └── Table: raw_measurement
```

- **Схема `core` (Ядро системи):** Призначена для збереження валідованих бізнес-сутностей предметної області (прилади та їхні сенсори). Забезпечує дотримання реляційної цілісності через `PRIMARY KEY` та `FOREIGN KEY`.
- **Схема `staging` (Буферна зона завантаження):** Використовується в ETL/ELT-процесах як проміжний накопичувач "сирих" даних, що імпортуються з зовнішніх джерел (CSV-файлів, черг повідомлень). Поля таблиць у `staging` зазвичай мають слабку типізацію (`text`), що унеможливлює падіння імпорту через помилки форматування та дозволяє провести очищення й валідацію даних перед перенесенням у схему `core`.

### 2.3. Порівняння методів доступу до метаданих: `pg_catalog` проти `information_schema`

| Критерій | Системні каталоги `pg_catalog` | Представлення `information_schema` |
| :--- | :--- | :--- |
| **Походження** | Внутрішнє системне ядро PostgreSQL. | Міжнародний стандарт ANSI/ISO SQL. |
| **Приклади таблиць** | `pg_database`, `pg_namespace`, `pg_class`, `pg_attribute` | `information_schema.schemata`, `tables`, `columns` |
| **Зміст даних** | Низькорівневі метадані: OID, `relkind`, бінарні маски прав, внутрішні системні номери. | Стандартизовані назви типів, перелік стовпців, ознаки `is_nullable`, порядкові номери позицій. |
| **Швидкодія** | Максимальна (нативні внутрішні C-структури ядра). | Повільніша (складні views з численними фільтрами безпеки та об'єднаннями). |
| **Переносимість** | Специфічна виключно для PostgreSQL. | Висока (сумісна з MySQL, MS SQL Server тощо). |

### 2.4. Сутність ідентифікатора OID (Object Identifier)

- **`OID`** — це внутрішній 32-бітний беззнаковий цілочисельний ідентифікатор (`unsigned int`, діапазон від 0 до 4 × 10⁹, тобто понад 4 млрд), який використовується ядром PostgreSQL для однозначної адресації системних об'єктів (баз даних, схем, таблиць, типів даних, функцій, індексів).
- **Важливе застереження:** OID не є унікальним глобально для прикладних даних і не гарантує безперервності після переповнення 32-бітного лічильника. У сучасних версіях PostgreSQL (`v12+`) таблиці створюються без системного стовпця OID за замовчуванням. Для прикладних сутностей слід використовувати стандартні первинні ключі: `bigint GENERATED ALWAYS AS IDENTITY` або `uuid`.

### 2.5. Порівняння механізмів масового імпорту CSV

При імпорті великих масивів даних стандартні одиничні запити `INSERT` стають вузьким місцем через накладні витрати на парсинг кожного SQL-виразу та створення окремих транзакцій. Для швидкого завантаження використовується механізм `COPY`:

| Метод | Рівень виконання | Локація файлу | Особливості застосування у хмарі |
| :--- | :--- | :--- | :--- |
| **`COPY ... FROM '/path'`** | Серверний процес PostgreSQL | Файлова система **сервера** БД | **Не працює у Supabase.** Сервер у хмарі AWS не має доступу до локального диска комп'ютера студента. |
| **`\copy ... FROM 'path'`** | Клієнтська утиліта `psql` | Файлова система **клієнта** | Читає локальний файл на клієнті та передає його серверу через спеціальний підпротокол потоку даних. |
| **`psycopg cur.copy()`** | Клієнтський скрипт Python | Файлова система **клієнта** | Python відкриває локальний файл і надсилає його частинами (чанками по 8192 байти) за протоколом `COPY ... FROM STDIN`. Ідеальний метод для хмарних БД. |

### 3.2. Створення схем і таблиць (DDL) та інспекція структури

Виконано створення схем `core`, `staging` та цільових таблиць:

```text
Підключення до Supabase PostgreSQL...
Підключення успішно встановлено!

--- Створення схем ---
Схеми 'core' та 'staging' успішно створено.

--- Створення таблиць ---
Таблиці 'core.device', 'core.sensor' та 'staging.raw_measurement' створено.

--- Перевірка створених таблиць ---
Таблиця: core.device
Таблиця: core.sensor
Таблиця: staging.raw_measurement

--- Структура таблиці core.sensor ---
Колонка: sensor_id, Тип: bigint, Nullable: NO
Колонка: device_id, Тип: bigint, Nullable: YES
Колонка: sensor_code, Тип: text, Nullable: NO
Колонка: quantity, Тип: text, Nullable: YES
Колонка: unit_symbol, Тип: text, Nullable: YES
```

#### Реалізований SQL DDL-код:
```sql
-- Створення просторів імен
CREATE SCHEMA IF NOT EXISTS core;
CREATE SCHEMA IF NOT EXISTS staging;

-- Таблиця приладів
CREATE TABLE IF NOT EXISTS core.device (
    device_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    device_name text NOT NULL,
    model text
);

-- Таблиця сенсорів із зовнішнім ключем
CREATE TABLE IF NOT EXISTS core.sensor (
    sensor_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    device_id bigint REFERENCES core.device(device_id),
    sensor_code text NOT NULL,
    quantity text,
    unit_symbol text
);

-- Таблиця буфера імпорту
CREATE TABLE IF NOT EXISTS staging.raw_measurement (
    sensor_code text,
    measured_at text,
    value_text text
);
```

#### Аналіз структури:
- Застосовано стандартний синтаксис SQL:2003 `GENERATED ALWAYS AS IDENTITY` замість застарілого типу `SERIAL`. Це запобігає випадковому ручному перетиранню первинного ключа та усуває пряму прив'язку до окремого імені послідовності.
- Стовпець `core.sensor.device_id` має обмеження цілісності `REFERENCES core.device(device_id)`, що блокує появу "підвішених" записів сенсорів без існуючого приладу.

### 3.4. Потоковий імпорт CSV через протокол `COPY FROM STDIN`

## 5. Відповіді на контрольні питання (Розділ 35 методички)

### 1. Що таке PostgreSQL?
**Відповідь:** PostgreSQL — це потужна об'єктно-реляційна система керування базами даних (СКБД) з відкритим вихідним кодом, що повністю підтримує транзакційні властивості ACID, стандарти ANSI SQL, складні типи даних, розширення та високу масштабованість.

### 2. Що означає клієнт-серверна архітектура?
**Відповідь:** Це модель взаємодії програмного забезпечення, за якої задачі розподіляються між постачальником ресурсів/послуг (**сервером**) та замовником послуг (**клієнтом**). Клієнт ініціює сесію зв'язку по мережевому протоколу, надсилає команди та отримує результати, а серверний процес інтерпретує SQL, керує буферним пулом пам'яті, дисковими сховищами та транзакціями.

### 3. Яку роль у цій лабораторній роботі виконує Supabase?
**Відповідь:** Supabase виступає хмарною платформою (Backend-as-a-Service, BaaS), що надає попередньо сконфігурований, керований та захищений екземпляр сервера PostgreSQL 17 у хмарі AWS разом із шлюзом пулу з'єднань (PgBouncer Pooler).

### 4. Де фізично працює сервер PostgreSQL при використанні Supabase?
**Відповідь:** Сервер фізично працює у дата-центрі хмарного провайдера AWS у вибраному регіоні (наприклад, `eu-central-1` у Франкфурті або `eu-west-1` в Ірландії) на виділених віртуальних машинах під керуванням Linux.

### 5. Для чого використовується бібліотека `psycopg`?
**Відповідь:** `psycopg` — це офіційний високоефективний драйвер (адаптер) СУБД PostgreSQL для мови Python, що реалізує стандартний інтерфейс Python DB-API 2.0 і підтримує нативні протоколи PostgreSQL (включаючи `COPY FROM STDIN`, бінарні передачі та асинхронні виклики).

### 6. Що таке база даних PostgreSQL?
**Відповідь:** База даних — це іменований логічний контейнер найвищого рівня в межах одного екземпляра (кластера) СУБД, що володіє повною ізоляцією даних. Об'єкти з різних баз даних не можуть об'єднуватися в одному запиті без спеціальних розширень (`dblink`, `postgres_fdw`).

### 7. Що таке схема PostgreSQL?
**Відповідь:** Схема (namespace) — це логічний простір імен *усередині* конкретної бази даних. Вона дозволяє структурувати таблиці, типи та функції, розмежовувати права доступу користувачів і запобігати колізіям однакових імен таблиць.

### 8. Чим схема відрізняється від таблиці?
**Відповідь:** Схема є контейнером (каталогом простору імен), який групує множину об'єктів. Таблиця є безпосередньо реляційним об'єктом збереження структурованих даних, що складається зі стовпців визначених типів та рядків записів.

### 9. Для чого використовується `information_schema`?
**Відповідь:** `information_schema` — це визначений стандартом ANSI SQL набір системних подань (views), призначений для уніфікованого програмного читання метаданих (переліку схем, таблиць, стовпців, обмежень) незалежно від вендора СУБД.

### 10. Що містить системний каталог `pg_database`?
**Відповідь:** Системний каталог `pg_database` містить метадані про всі бази даних, наявні в поточному кластері PostgreSQL: їхні системні OID, імена (`datname`), ідентифікатори власників (`datdba`), кодування символів (`encoding`) та параметри колізій.

### 11. Що містить системний каталог `pg_namespace`?
**Відповідь:** Системний каталог `pg_namespace` зберігає інформацію про всі схеми (простори імен) поточної бази даних, включаючи їхні системні OID (`oid`), текстові назви (`nspname`) та OID власників схеми (`nspowner`).

### 12. Що містить системний каталог `pg_class`?
**Відповідь:** `pg_class` описує всі відношення (relations) у базі даних: звичайні таблиці (`relkind = 'r'`), індекси (`'i'`), подання (`'v'`), матеріалізовані подання (`'m'`), послідовності (`'S'`) та тостові таблиці (`'t'`), їхні OID та прив'язку до простору імен `relnamespace`.

### 13. Що таке OID?
**Відповідь:** `OID` (Object Identifier) — це 32-бітне ціле беззнакове число, яке СУБД PostgreSQL внутрішньо призначає сутностям (базам, схемам, таблицям, типам) як системний первинний ключ для лінкування записів між каталогами ядра.

### 14. Для чого використовується команда `SELECT`?
**Відповідь:** Це основна DQL (Data Query Language) команда мови SQL, призначена для читання, фільтрації, сортування, агрегації та обчислення даних з однієї або кількох таблиць і подань.

### 15. Для чого використовується `conn.commit()`?
**Відповідь:** Метод `commit()` підтверджує і фіксує поточну транзакцію на сервері БД. Усі внесені зміни (DDL або DML) стають атомарними, зберігаються на постійному диску і стають видимими для інших клієнтських підключень.

### 16. Що робить функція `cur.execute()`?
**Відповідь:** Функція надсилає текстовий SQL-запит (із необов'язковим передаванням параметрів) на сервер СУБД для його компіляції, оптимізації плану та безпосереднього виконання в межах відкритого курсору.

### 17. Що робить функція `cur.fetchone()`?
**Відповідь:** Завантажує один наступний кортеж (рядок) з результуючого набору даних, повернутого сервером після виконання запиту, або повертає `None`, якщо дані закінчилися.

### 18. Що робить функція `cur.fetchall()`?
**Відповідь:** Завантажує всі залишкові рядки результуючого набору виконаного запиту у вигляді списку кортежів Python у клієнтську оперативну пам'ять.

### 19. Для чого використовується `conn.close()`?
**Відповідь:** Закриває відкритий мережевий TCP-сокет і коректно завершує клієнтську сесію з сервером СУБД, вивільняючи ресурси бекенд-процесу PostgreSQL та вільні слоти пулера з'єднань.

### 20. Чому звичайний `COPY FROM 'C:\...'` не підходить для хмарного PostgreSQL?
**Відповідь:** Команда `COPY FROM '/шлях'` є серверною командою: вона вимагає від ядра СУБД читання файлу безпосередньо з локального диска хоста, де запущено сервер PostgreSQL. Хмарний сервер Supabase фізично не має доступу до локальної файлової системи машини студента, тому така спроба завершиться помилкою відсутності файлу.

### 21. Чим відрізняються `COPY` та `\copy`?
**Відповідь:** `COPY` — це серверна SQL-команда ядра БД, що оперує файлами сервера. `\copy` — це клієнтський макрос термінала `psql`, який перехоплює команду, читає локальний файл на клієнті та транслює його серверу за допомогою підпротоколу `COPY ... FROM STDIN`.

### 22. Яку роль при імпорті CSV у цій роботі виконує Python?
**Відповідь:** Python виконує роль розумного клієнта: скрипт відкриває локальний файл `measurements.csv`, зчитує вміст блоками пам'яті (чанками) і передає потік даних через драйвер `psycopg` у хмарне з'єднання за допомогою клієнтського механізму `cur.copy("... FROM STDIN")`.

### 23. Чому пароль бази даних не слід записувати у звіт?
**Відповідь:** Відповідно до стандартів комп'ютерної безпеки, автентифікаційні паролі є конфіденційними секретами. Фіксація пароля у звітах або його публікація у відкритих репозиторіях (Git) призводить до компрометації інфраструктури, несанкціонованого доступу та витоку даних.
