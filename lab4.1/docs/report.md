## 2. Теоретичні відомості та архітектурний аналіз

### 2.1. Часова модель даних та переваги `timestamptz` у хмарі (Supabase)

Класичні реляційні СУБД надають базові типи `date` та `time`. Однак у розподілених веб-застосунках виникає потреба збереження повної мітки моменту події. PostgreSQL розрізняє:
- `timestamp` (`without time zone`): наївне представлення дати й часу без прив'язки до географічного зміщення. При перенесенні між серверами з різними налаштуваннями локального часу виникає ризик спотворення інформації.
- `timestamptz` (`with time zone`): промисловий стандарт збереження часу. **Сервер PostgreSQL фізично завжди трансформує значення в UTC (Universal Coordinated Time) зі зміщенням `+00`**. При зчитуванні клієнтом СУБД автоматично перераховує UTC у часовий пояс поточної клієнтської сесії (`TimeZone`).

У протоколі цієї лабораторної роботи наочно зафіксовано цей механізм: при вставці значень у часовому поясі України (`UTC+2`):
```sql
tstzrange('2026-09-20 10:00+02', '2026-09-20 11:00+02')
```
сервер зберіг значення в каталозі у нормалізованому вигляді:
```text
["2026-09-20 08:00:00+00","2026-09-20 09:00:00+00")
```
що повністю усуває неоднозначності при обміні даними між географічно розподіленими клієнтами.

### 2.2. Арифметика інтервалів та вбудовані часові функції

- **Тип `interval`:** На відміну від статичних позначок моменту, `interval` представляє часову тривалість (наприклад, `08:30:00` або `3 days 04:15:00`). Різниця між двома точками в часі (`end_time - start_time`) автоматично породжує значення типу `interval`.
- **Функція `EXTRACT(field FROM source)`:** Дозволяє ізолювати конкретне числове значення з дати/часу:
  - `EXTRACT(DOW FROM work_date)`: повертає день тижня (Day of Week), де `0` — неділя, `1` — понеділок, `2` — вівторок, `3` — середа тощо.
  - `EXTRACT(MONTH FROM work_date)`: повертає порядковий номер місяця (від 1 до 12).
- **Функція `AGE(timestamp1, timestamp2)`:** Обчислює точну різницю між двома часовими точками. У формі з одним аргументом `AGE(created_at)` вимірює вік запису відносно поточної дати/часу (`current_date` або `now()`).
- **Функція `TO_CHAR(source, format)`:** Здійснює безпечне шаблонне форматування дати у зручний для користувача вигляд (наприклад, `'DD.MM.YYYY'`).

### 2.3. Математика типів діапазонів (Range Types) та семантика меж

Тип «діапазон» (**Range Type**) — це атомарний тип даних, що представляє інтервал значень між нижньою (`lower`) та верхньою (`upper`) межами.

Синтаксис меж відповідає строгим математичним позначенням інтервалів:
- `[` — нижня межа включена (**inclusive**).
- `]` — верхня межа включена (**inclusive**).
- `(` — нижня межа виключена (**exclusive**).
- `)` — верхня межа виключена (**exclusive**).

**Принцип напіввідкритого інтервалу `[)`:**  
За замовчуванням PostgreSQL приводить часові інтервали до канонічної форми `[lower, upper)`. Це є математично бездоганним рішенням для дискретних та неперервних процесів:  
Якщо перша зміна завершується в `11:00:00`, а наступна починається в `11:00:00`, запис у вигляді:
- Інтервал 1: `[10:00, 11:00)` (містить точки до 10:59:59.999...)
- Інтервал 2: `[11:00, 12:30)` (включає рівно 11:00:00)

**не призводить до колізії перетину**, оскільки точка `11:00:00` належить виключно другому інтервалу.

### 2.4. Обмеження `EXCLUDE USING gist` та роль модуля `btree_gist`

Традиційне реляційне обмеження `UNIQUE` перевіряє виключно скалярну рівність (`val1 = val2`). Воно неспроможне виявити частковий перетин інтервалів: наприклад, періоди `10:00–12:00` та `10:30–11:30` не є рівними за значеннями меж, проте вони фізично конфліктують.

Для вирішення цієї задачі PostgreSQL надає індексне обмеження виключення:
```sql
EXCLUDE USING gist (room_id WITH =, period WITH &&)
```

```text
Паралельні транзакції
        │
        ├─► INSERT INTO room_bookings (room_id=1, period='[10:00, 11:00)') ──► УСПІХ (Зафіксовано в GiST)
        │
        └─► INSERT INTO room_bookings (room_id=1, period='[10:45, 11:15)')
                    │
                    ▼
           GiST Index Scan:
           - room_id = 1 ? ──► ТАК (знайдено збіг скаляра)
           - period && existing_period ? ──► ТАК (перетин 10:45-11:00)
                    │
                    ▼
           ERROR: conflicting key value violates exclusion constraint!
```

#### Чому необхідне розширення `btree_gist`?
Індекс GiST (Generalized Search Tree) оптимізований для багатовимірних даних, просторових об'єктів та діапазонів (підтримує оператор `&&`). Проте GiST нативно не вміє індексувати скалярні типи даних (`int`, `text`, `uuid`) за оператором точної рівності `=`.  
Розширення **`btree_gist`** реалізує інтерфейси B-дерева всередині індексу GiST, дозволяючи в одному виразі обмеження поєднати скалярну рівність (`room_id WITH =`) та перетин діапазонів (`period WITH &&`).

### 2.5. Порівняння: Range Types проти двох окремих стовпців (`start_time`, `end_time`)

| Критерій | Зберігання в окремих полях (`start_time`, `end_time`) | Використання Range Type (`period tstzrange`) |
| :--- | :--- | :--- |
| **Атомарність моделі** | Порушена: інтервал розділений на дві незалежні змінні. | Повна: інтервал є єдиним атомарним значенням. |
| **Перевірка перетину** | Громіздкі логічні вирази: `(A.start < B.end AND A.end > B.start)`. Схильність до логічних помилок на межах. | Лаконічний та математично точний оператор: `A.period && B.period`. |
| **Захист від колізій** | `UNIQUE` не працює. Потрібні складні серверні тригери з блокуванням таблиці (`FOR UPDATE`), що обмежує паралелізм. | Декларативне обмеження ядра СУБД: `EXCLUDE USING gist (... WITH &&)` без написання коду. |
| **Індексація** | B-tree індекси неефективні для пошуку перекриттів на великих обсягах даних. | Швидкий просторовий пошук через індекс GiST / SP-GiST за лігарифмічний час. |
| **Межі інтервалу** | Складно визначити, чи включена точка межі (потрібні додаткові прапорці). | Вбудований контроль включення/виключення: `[)`, `[]`, `()`. |

### 3.3. Рівень 2: Підключення `btree_gist` та створення таблиці бронювань

Активовано розширення та створено таблицю бронювань із обмеженням виключення:
```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE lab41.room_bookings (
    id         serial PRIMARY KEY,
    room_id    int NOT NULL,
    booked_by  text NOT NULL,
    period     tstzrange NOT NULL,
    EXCLUDE USING gist (room_id WITH =, period WITH &&)
);
```

Додано базові безконфліктні бронювання:
```sql
INSERT INTO lab41.room_bookings (room_id, booked_by, period)
VALUES (1, 'Кафедра ІТ', tstzrange('2026-09-20 10:00+02', '2026-09-20 11:00+02'));

INSERT INTO lab41.room_bookings (room_id, booked_by, period)
VALUES (1, 'Кафедра метрології', tstzrange('2026-09-20 11:00+02', '2026-09-20 12:30+02'));

INSERT INTO lab41.room_bookings (room_id, booked_by, period)
VALUES (2, 'Деканат', tstzrange('2026-09-20 10:30+02', '2026-09-20 11:30+02'));
```

Фактичний стан таблиці `room_bookings`:
```text
postgres=> SELECT * FROM lab41.room_bookings;

----+---------+--------------------+-----------------------------------------------------
  1 |       1 | Кафедра ІТ         | ["2026-09-20 08:00:00+00","2026-09-20 09:00:00+00")
  2 |       1 | Кафедра метрології | ["2026-09-20 09:00:00+00","2026-09-20 10:30:00+00")
```

### 3.4. Верифікація цілісності: негативне тестування конфлікту накладання бронювань

Виконано спробу вставки бронювання, що накладається на наявні часові інтервали кімнати 1:
```sql
INSERT INTO lab41.room_bookings (room_id, booked_by, period)
VALUES (1, 'Студентський деканат', tstzrange('2026-09-20 10:45+02', '2026-09-20 11:15+02'));
```

**Фактична реакція ядра СУБД:**
```text
ERROR:  conflicting key value violates exclusion constraint "room_bookings_room_id_period_excl"
DETAIL:  Key (room_id, period)=(1, ["2026-09-20 08:45:00+00","2026-09-20 09:15:00+00")) conflicts with existing key (room_id, period)=(1, ["2026-09-20 08:00:00+00","2026-09-20 09:00:00+00")).
```
*Обмеження GiST заблокувало вставку конфліктного запису на рівні ядра бази даних.*

### 3.5. Оператори діапазонів: перетин (`&&`), межі (`lower`/`upper`) та входження точки (`@>`)

#### Пошук перетинів із контрольним інтервалом через оператор `&&`:
```sql
SELECT id, room_id, booked_by, period
FROM lab41.room_bookings
WHERE room_id = 1
  AND period && tstzrange('2026-09-20 10:30+02', '2026-09-20 11:15+02');
```
Результат виконання:
```text
 id | room_id |     booked_by      |                       period                        
----+---------+--------------------+-----------------------------------------------------
  1 |       1 | Кафедра ІТ         | ["2026-09-20 08:00:00+00","2026-09-20 09:00:00+00")
  2 |       1 | Кафедра метрології | ["2026-09-20 09:00:00+00","2026-09-20 10:30:00+00")
(2 rows)
```
*Запит повернув обидва записи, оскільки шуканий проміжок 10:30–11:15 частково накладається як на перший інтервал (до 11:00), так і на другий (після 11:00).*

#### Отримання меж та перевірка приналежності фіксованого часу через `@>`:
```sql
SELECT
    booked_by,
    lower(period) AS starts_at,
    upper(period) AS ends_at,
    period @> TIMESTAMPTZ '2026-09-20 11:15+02' AS contains_1115
FROM lab41.room_bookings;
```
Результат виконання:
```text
     booked_by      |       starts_at        |        ends_at         | contains_1115 
--------------------+------------------------+------------------------+---------------
 Кафедра ІТ         | 2026-09-20 08:00:00+00 | 2026-09-20 09:00:00+00 | f
 Кафедра метрології | 2026-09-20 09:00:00+00 | 2026-09-20 10:30:00+00 | t
```


Фактичний перелік бронювань для кімнати 1:
```text

---------+--------------------+-----------------------------------------------------
       1 | Кафедра ІТ         | ["2026-09-20 08:00:00+00","2026-09-20 09:00:00+00")
       1 | Кафедра метрології | ["2026-09-20 09:00:00+00","2026-09-20 10:30:00+00")
       1 | Науковий сектор    | ["2026-09-20 12:00:00+00","2026-09-20 13:30:00+00")
       2 | Деканат            | ["2026-09-20 08:30:00+00","2026-09-20 09:30:00+00")
(4 rows)
```

#### SQL-запит пошуку вільних інтервалів:
```sql
WITH ordered_bookings AS (
    SELECT
        room_id,
        booked_by,
        lower(period) AS cur_start,
        upper(period) AS cur_end,
        LEAD(lower(period)) OVER (
            PARTITION BY room_id
            ORDER BY lower(period)
        ) AS next_start
    FROM lab41.room_bookings
    WHERE room_id = 1
      AND period && tstzrange('2026-09-20 00:00+02', '2026-09-20 23:59:59+02')
)
SELECT
    room_id,
    cur_end AS free_from,
    next_start AS free_to,
    (next_start - cur_end) AS free_duration,
    tstzrange(cur_end, next_start, '[)') AS free_slot
FROM ordered_bookings
WHERE next_start IS NOT NULL
  AND next_start > cur_end;
```

Фактичний результат виконання запиту:
```text

---------+------------------------+------------------------+---------------+-----------------------------------------------------
       1 | 2026-09-20 10:30:00+00 | 2026-09-20 12:00:00+00 | 01:30:00      | ["2026-09-20 10:30:00+00","2026-09-20 12:00:00+00")
(1 row)
```
*Запит безпомилково ідентифікував «вікно» між завершенням бронювання Кафедри метрології (12:30+02 / 10:30 UTC) та початком Наукового сектора (14:00+02 / 12:00 UTC) тривалістю 1 година 30 хвилин.*

## 5. Відповіді на контрольні питання

### 1. У чому відмінність між типами `timestamp` і `timestamptz`? Чому для Supabase рекомендовано використовувати саме `timestamptz`?
**Відповідь:**  
`timestamp` (`without time zone`) зберігає значення дати й часу в «наївному» вигляді без жодної інформації про часовий пояс. Якщо клієнти надсилають дані з різних куточків світу, сервер не здатний визначити їхній абсолютний фізичний момент у часі.  
`timestamptz` (`with time zone`) автоматично конвертує будь-яке введене значення у єдиний світовий стандарт — **UTC (зі зміщенням `+00`)** і зберігає його у такому вигляді. Під час вибірки ядро PostgreSQL автоматично перераховує UTC у часовий пояс сесії підключеного клієнта. Оскільки Supabase — це розподілена хмарна платформа, до якої підключаються сервери, браузери та мобільні пристрої з різних часових поясів, використання `timestamptz` є обов'язковим стандартом для збереження глобальної узгодженості даних.

### 2. Що таке тип «діапазон» (range type) і які межі він може включати чи виключати?
**Відповідь:**  
Тип «діапазон» — це вбудований у PostgreSQL складений атомарний тип даних, що представляє неперервний або дискретний відрізок значень між нижньою (`lower`) та верхньою (`upper`) межами.  
Межі регулюються математичним синтаксисом:
- Квадратні дужки `[` або `]` позначають включення граничного значення (**inclusive**).
- Круглі дужки `(` або `)` позначають виключення граничного значення (**exclusive**).  
Діапазони в PostgreSQL за замовчуванням нормалізуються до напіввідкритого вигляду `[lower, upper)`. Також діапазони підтримують нескінченні межі (наприклад, `[10, infinity)` або `(, 0)`), перевірка яких здійснюється функціями `lower_inf()` та `upper_inf()`.

### 3. Яке призначення оператора `&&` для діапазонних типів? Наведіть приклад його застосування.
**Відповідь:**  
Оператор `&&` (**overlap**) призначений для перевірки факту взаємного геометричного перетину або накладання двох діапазонів. Він повертає булеве значення `true`, якщо обидва діапазони мають хоча б одну спільну точку, і `false` — якщо вони повністю ізольовані.  
*Приклад:*
```sql
tstzrange('2026-09-20 10:00+02', '2026-09-20 11:00+02') && 
tstzrange('2026-09-20 10:45+02', '2026-09-20 11:30+02')
```
Вираз повертає `true`, оскільки проміжок часу з 10:45 до 11:00 є спільним для обох інтервалів. При цьому стикування `[10:00, 11:00)` та `[11:00, 12:00)` поверне `false`.

### 4. Для чого потрібне розширення `btree_gist` під час створення обмеження `EXCLUDE` на комбінації «звичайний стовпець + діапазон»?
**Відповідь:**  
Обмеження `EXCLUDE` функціонує на базі індексів **GiST** (Generalized Search Tree), які спеціалізуються на операторах перетину (`&&`), входження (`@>`) та просторових співвідношеннях. Проте GiST-індекси за замовчуванням не мають реалізації операторних класів для стандартних скалярних типів даних (`int`, `text`, `uuid`) за оператором точної рівності `=`.  
Розширення `btree_gist` додає до ядра GiST операторні класи B-дерева. Завдяки цьому стає можливим створити комбіноване обмеження `EXCLUDE USING gist (room_id WITH =, period WITH &&)`, де скалярний ідентифікатор кімнати перевіряється на точну рівність `=`, а часовий інтервал — на перетин `&&`.

### 5. Чим відрізняються функції `EXTRACT()` та `AGE()`? У яких випадках доцільно застосовувати кожну з них?
**Відповідь:**  
- **`EXTRACT(field FROM source)`** вилучає та повертає одне чисельне значення конкретного атрибута (компонента) дати або часу — наприклад, день тижня (`DOW`), порядковий номер місяця (`MONTH`), рік (`YEAR`) чи годину (`HOUR`). Застосовується для аналітики, фільтрації, партиціювання таблиць та календарного групування (`GROUP BY`).
- **`AGE(timestamp1, [timestamp2])`** розраховує повну різницю між двома мітками часу і повертає значення типу `interval` у зручному для сприйняття людиною форматі (роки, місяці, дні, години, хвилини, секунди). Застосовується для розрахунку стажу, віку людини, тривалості життєвого циклу замовлення або часу від моменту створення запису в системі.

### 6. Яку практичну задачу вирішує обмеження `EXCLUDE USING gist` на прикладі таблиці бронювань?
**Відповідь:**  
Це обмеження вирішує фундаментальну проблему паралелізму — **запобігання стану перегонів (race condition) та подвійному бронюванню фізичних ресурсів (double-booking)** на рівні ядра СУБД.  
Без `EXCLUDE` перевірка доступності ресурсу потребувала б ручного блокування рядків у транзакціях (`SELECT ... FOR UPDATE`), що сповільнює роботу системи або створює ризики пропуску колізій при паралельних веб-запитах. Обмеження `EXCLUDE USING gist` декларативно та з мінімальними накладними витратами гарантує, що база даних апаратно відхилить будь-яку транзакцію, яка намагається зареєструвати той самий ресурс на час, що перетинається з уже підтвердженим інтервалом.

## 6. Висновки

1. **Опановано розширену часову модель PostgreSQL у хмарі Supabase:** Досліджено специфіку функціонування часових типів `date`, `time`, `timestamp`, `timestamptz` та `interval`. Практично підтверджено, що використання `timestamptz` є безальтернативним стандартом для хмарних сервісів, оскільки воно забезпечує прозору нормалізацію даних до єдиної шкали **UTC**.
2. **Засвоєно аналітичний інструментарій роботи з часом:** Реалізовано обчислення тривалості змін через часову арифметику, отримано календарні компоненти за допомогою `EXTRACT()`, розраховано часовий вік сутностей через `AGE()` та виконано строкове форматування через `TO_CHAR()`.
3. **Досліджено типи діапазонів (Range Types):** На прикладі `tstzrange` та `numrange` вивчено переваги зберігання інтервалів як атомарних сутностей. Доведено зручність використання стандартного напіввідкритого інтервалу `[)` для безконфліктного стикування сусідніх інтервалів на межах.
4. **Реалізовано декларативний захист від колізій через `EXCLUDE USING gist`:** Практично підтверджено неефективність класичного `UNIQUE` для перевірки накладання інтервалів. За допомогою розширення `btree_gist` реалізовано комбіноване обмеження скалярів та діапазонів, що на рівні ядра СУБД заблокувало спробу подвійного бронювання кімнати з помилкою `conflicting key value violates exclusion constraint`.
5. **Розроблено аналітичний запит виявлення вільних слотів через `LEAD()`:** За допомогою віконної функції `LEAD()` реалізовано алгоритм аналізу часових проміжків між впорядкованими бронюваннями, що дозволило точно знайти вільне вікно для кімнати 1 тривалістю 1 година 30 хвилин.
6. **Доведено перевагу типів діапазонів над окремими стовпцями:** Порівняльний аналіз показав, що діапазонні типи скорочують обсяг SQL-коду, усувають складні логічні конструкції перевірки меж `(start < end AND end > start)`, унеможливлюють логічні колізії та забезпечують швидкий пошук за рахунок просторових GiST-індексів.
