## 2. Теоретичні відомості та архітектурний аналіз

### 2.1. Скалярні та сурогатні типи: `IDENTITY` проти `SERIAL`, `NUMERIC` проти `FLOAT`

#### 1. Стандарт `GENERATED ALWAYS AS IDENTITY` проти застарілого `SERIAL`:
Історично в PostgreSQL автоінкрементні первинні ключі створювалися псевдотипом `SERIAL`, який автоматично створював зв'язану послідовність (`sequence`) та призначав вираз `DEFAULT nextval('seq_name')`. Проте `SERIAL` має суттєві недоліки:
- Не є стандартом ANSI SQL.
- Дозволяє випадкову явну вставку довільного `id`, що в майбутньому призводить до помилок колізії первинного ключа `duplicate key value violates unique constraint`, коли лічильник послідовності наздоганяє вручну вставлене число.
Конструкція `GENERATED ALWAYS AS IDENTITY` відповідає стандарту SQL:2003. Вона блокує спроби клієнта вручну передати значення в стовпець `id` без спеціальної директиви `OVERRIDING SYSTEM VALUE`, забезпечуючи абсолютну цілісність сурогатних ключів.

#### 2. Фінансова точність `NUMERIC(precision, scale)`:
Типи з рухомою комою (`real`, `double precision`) зберігають числа у двійковому форматі IEEE 754. Вони не здатні точно представити більшість десяткових дробів (наприклад, `0.1` або `0.7`), що викликає накопичення мікроскопічних похибок заокруглення під час сумування грошових сум. Тип `NUMERIC(10, 2)` (синонім `DECIMAL`) зберігає числа у точній десятковій формі довільної точності (10 цифр загалом, 2 знаки після коми) і є промисловим стандартом для фінансових і торговельних систем.

### 2.2. Одновимірні масиви в PostgreSQL (`TEXT[]`): переваги та механіка індексації

PostgreSQL надає вбудовану підтримку масивів для будь-якого базового типу даних. Стовпець `tags TEXT[]` дозволяє зберігати невеликий упорядкований набір текстових міток без створення проміжної дочірньої таблиці зв'язку (Many-to-Many):
- **1-based індексація:** У більшості мов програмування масиви нумеруються з `0`. У стандартному SQL і PostgreSQL перший елемент масиву має індекс `1` (`tags[1]`). Звернення за індексом `0` повертає `NULL`, якщо масив не було перевизначено користувачем із кастомним діапазоном індексів.
- **Предикат `= ANY(array)`:** Дозволяє ефективно перевірити факт рівності скалярного значення хоча б одному елементу масиву без повного розгортання колекції:
  ```sql
  WHERE 'терміново' = ANY(tags)
  ```
- **Функція `unnest(array)`:** Здійснює реляційне розгортання («розплющення») масиву: кожен елемент повертається окремим рядком, що дозволяє застосовувати до елементів масиву реляційні оператори `GROUP BY`, `JOIN` та агрегатні функції.

### 2.3. Документоорієнтований тип `JSONB`: бінарна декомпозиція та оператори пошуку

На відміну від застарілого типу `json` (який зберігає вихідний текст документа "як є", вимагаючи синтаксичного розбору при кожному зверненні), тип `jsonb` декомпонує JSON у внутрішній оптимізований двійковий формат:
- Видаляє зайві пробіли та символи форматування.
- Дедуплікує повторювані ключі всередині одного об'єкта (зберігається останнє значення).
- Забезпечує пряму адресацію та миттєвий пошук ключів.
- Підтримує побудову інвертованих індексів **GIN (Generalized Inverted Index)**.

#### Оператори навігації та пошуку:
| Оператор | Тип аргументу | Тип результату | Призначення та особливості |
| :--- | :--- | :--- | :--- |
| `->` | `text` або `int` | `jsonb` | Витягує поле об'єкта або елемент масиву. Зберігає JSONB-тип, дозволяючи будувати ланцюжки переходів: `metadata->'payment'->'method'`. |
| `->>` | `text` або `int` | `text` | Витягує кінцеве значення поля або елемента та конвертує його в скалярний рядок `text`. |
| `@>` | `jsonb` | `boolean` | Оператор входження (**containment**). Перевіряє, чи містить лівий документ у собі структуру, задану правим документом. Працює з GIN-індексами. |
| `jsonb_array_elements_text()` | `jsonb` | `setof text` | Розгортає елементи JSON-масиву в набір рядків реляційної таблиці. |

#### Необхідність явного приведення типів (`::integer`, `::boolean`):
Оскільки оператор `->>` завжди повертає тип `text`, вирази на кшталт `metadata->>'priority' > 3` виконують лексикографічне (посимвольне) порівняння рядків, а не математичне числове порівняння. Для коректної логіки обов'язковим є явне приведення:
```sql
WHERE (metadata->>'priority')::integer > 3
```

### 2.4. Часові пояси: архітектура UTC у хмарі та семантика `AT TIME ZONE`

Сервер PostgreSQL при використанні типу `TIMESTAMPTZ` **завжди зберігає значення в абсолютній системі координат — UTC (зі зміщенням +00)**.
- При надсиланні клієнтом позначки часу з локальним зміщенням (наприклад, `2026-10-04 22:09:14+03`) сервер конвертує її у внутрішній формат: `2026-10-04 19:09:14+00`.
- При запиті клієнта сервер трансформує UTC-час у поточний сеансовий часовий пояс (`SHOW timezone;`).
- Оператор **`AT TIME ZONE`** дозволяє динамічно перетворити час:
  - `timestamptz AT TIME ZONE 'zone'`: обчислює локальний календарний час у зазначеній географічній зоні та повертає тип `timestamp without time zone`.
  - `timestamp AT TIME ZONE 'zone'`: інтерпретує значення без поясу як локальний час зазначеної зони та конвертує його в абсолютний `timestamptz` (UTC).

### 2.5. Динамічна генерація рядів `generate_series` та техніка zero-loss календаря через `LEFT JOIN`

Функція `generate_series(start, stop, step)` формує неперервну віртуальну послідовність значень на льоту без необхідності створення постійних довідникових таблиць календаря на диску:
```sql
generate_series(DATE '2026-10-01', DATE '2026-10-31', INTERVAL '1 day')
```

#### Чому `LEFT JOIN` є обов'язковим для аналітичних звітів?
У реальних бізнес-системах замовлення надходять не щодня (наприклад, у вихідні або святкові дні замовлень може не бути).
- При використанні `INNER JOIN` дні з нульовою активністю випадуть із результату, що спотворить графіки продажів та статистику.
- `LEFT JOIN` гарантує, що всі згенеровані дні місяця потраплять у фінальний звіт.
- **Критична відмінність `COUNT(o.id)` від `COUNT(*)`:** Якщо за певну дату замовлень не було, `LEFT JOIN` повертає кортеж, де всі поля таблиці замовлень заповнені значеннями `NULL`. Агрегатна функція `COUNT(*)` рахує загальну кількість кортежів у групі й помилково поверне `1` (оскільки рядок існує). Натомість `COUNT(o.id)` ігнорує значення `NULL` і повертає математично коректне значення `0`.

## 5. Відповіді на контрольні питання

### 1. Чим `NUMERIC` відрізняється від `INTEGER`?
**Відповідь:**  
`INTEGER` — це 4-байтне ціле число (діапазон від -2 147 483 648 до +2 147 483 647), яке принципово не здатне зберігати дробову частину.  
`NUMERIC(precision, scale)` — це тип даних із фіксованою комою довільної точності. Параметр `precision` задає загальну кількість значущих цифр, а `scale` — кількість цифр після коми. На відміну від типів із рухомою комою (`REAL`, `DOUBLE PRECISION`), `NUMERIC` гарантує абсолютну точність арифметичних операцій і є обов'язковим для зберігання фінансових сум.

### 2. Що означає тип `TEXT[]`?
**Відповідь:**  
Синтаксис із квадратними дужками `[]` позначає одновимірний масив однорідних елементів типу `TEXT`. Цей тип дозволяє зберігати довільну кількість текстових рядків (наприклад, перелік тегів чи категорій) всередині однієї клітинки кортежу без необхідності створення окремої проміжної дочірньої таблиці зв'язку.

### 3. Для чого використовується функція `unnest`?
**Відповідь:**  
Функція `unnest(anyarray)` розгортає (розплющує) горизонтальний масив у вертикальний реляційний набір рядків (set of rows). Кожен елемент масиву стає окремим кортежем у результаті запиту. Це дозволяє застосовувати до елементів масиву стандартні реляційні оператори: сортування (`ORDER BY`), фільтрацію (`WHERE`), групування (`GROUP BY`) та агрегацію (`COUNT`, `SUM`).

### 4. Чим оператор `->` відрізняється від `->>` під час роботи з `JSONB`?
**Відповідь:**  
- Оператор `->` витягує поле об'єкта або елемент масиву і повертає його як **об'єкт типу `jsonb`**. Це дозволяє створювати послідовні ланцюжки переходів по вкладених структурах (наприклад: `metadata->'payment'->'details'`).
- Оператор `->>` витягує кінцеве значення поля і повертає його як скалярний тип **`text`**. Він використовується на останньому кроці навігації для відображення значення користувачу або для подальшого зведення типу (`::integer`, `::boolean`).

### 5. Що перевіряє оператор `@>`?
**Відповідь:**  
Оператор `@>` (**containment**, «містить») перевіряє, чи містить лівий документ `JSONB` у собі фрагмент структури або пару «ключ-значення», описану правим операндом.  
*Приклад:*
```sql
metadata @> '{"payment": {"method": "card"}}'::jsonb
```
поверне `true`, якщо в об'єкті `metadata` є об'єкт `payment`, всередині якого ключ `method` має значення `"card"`. Цей оператор на відміну від текстових пошуків підтримує апаратне прискорення через індекси GiST та GIN.

### 6. Для чого до значення JSONB іноді додають `::integer` або `::boolean`?
**Відповідь:**  
Оскільки оператор витягування кінцевого значення `->>` повертає результат виключно у текстовому форматі `text`, PostgreSQL сприймає його як звичайний рядок. Без явного приведення типи порівняння виконуються посимвольно (лексикографічно), що для чисел може давати некоректний результат (наприклад, рядок `'10'` лексикографічно менший за рядок `'2'`). Додавання `::integer` або `::boolean` зводить текстовий рядок до відповідного цільового скалярного типу, що дозволяє виконувати точні математичні або логічні порівняння (`> 3`, `= true`).

### 7. У чому різниця між `DATE` і `TIMESTAMPTZ`?
**Відповідь:**  
- `DATE` зберігає виключно календарну дату (рік, місяць, день) без часової складової (годин, хвилин, секунд) та без прив'язки до часового поясу.
- `TIMESTAMPTZ` (`timestamp with time zone`) зберігає абсолютний момент часу з точністю до мікросекунд. Сервер фізично нормалізує і зберігає значення завжди в **UTC (зміщення +00)**, а при вибірці автоматично трансформує його у часовий пояс поточної клієнтської сесії.

### 8. Що робить `AT TIME ZONE`?
**Відповідь:**  
Оператор `AT TIME ZONE` здійснює конвертацію між абсолютним моментом часу (`timestamptz`) та локальним представленням часу без зміщення (`timestamp without time zone`):
- Для `timestamptz`: обчислює дату й час у вказаній географічній зоні та повертає локальний `timestamp without time zone`.
- Для `timestamp without time zone`: інтерпретує значення як локальний час зазначеної зони та конвертує його в абсолютний `timestamptz` (переводить у UTC).

### 9. Які три основні аргументи має `generate_series(start, stop, step)`?
**Відповідь:**  
1. `start` — початкова точка діапазону (ціле число, дата або мітка часу).
2. `stop` — кінцева точка діапазону включно.
3. `step` — крок приросту послідовності. Для числових послідовностей це число (наприклад, `1`), а для часових послідовностей — значення типу `interval` (наприклад, `INTERVAL '1 day'` або `INTERVAL '1 hour'`).

### 10. Навіщо під час побудови календаря застосовується `LEFT JOIN`?
**Відповідь:**  
Якщо для з'єднання календаря з таблицею фактів (замовлень) використати `INNER JOIN`, у фінальну вибірку потраплять лише ті дні, коли було здійснено хоча б одну транзакцію. Усі дні без замовлень (вихідні, святкові або «порожні» робочі дні) будуть безповоротно втрачені з результату.  
`LEFT JOIN` гарантує повне збереження абсолютно всіх згенерованих днів місяця. Для днів без замовлень значення стовпців таблиці замовлень будуть `NULL`, а вираз `COUNT(o.id)` поверне `0`, що забезпечує цілісність бізнес-звітності.

## 6. Висновки

1. **Опановано комплексну систему типів даних PostgreSQL у хмарі Supabase:** Досліджено використання стандарту `GENERATED ALWAYS AS IDENTITY` для створення сурогатних ключів, точного типу `NUMERIC(10,2)` для захисту фінансових сум від похибок заокруглення та типу `INTERVAL` для розрахунку тривалості обробки.
2. **Засвоєно практичні прийоми роботи з масивами (`TEXT[]`):** Підтверджено особливості 1-based індексації в PostgreSQL, реалізовано ефективну фільтрацію за допомогою предиката `= ANY()`, підраховано кількість елементів через `array_length()` та розгорнуто одновимірні колекції в реляційні кортежі за допомогою функції `unnest()`.
3. **Досліджено документоорієнтований підхід із використанням `JSONB`:** Проаналізовано переваги бінарного формату перед класичним `JSON`, опановано навігаційні оператори `->` та `->>`, здійснено явне приведення типів (`::integer`, `::boolean`), реалізовано пошук входження структурних фрагментів через оператор `@>` та виконано розгортання вкладених списків за допомогою `jsonb_array_elements_text()`.
4. **Вивчено специфіку роботи з часовими поясами:** Практично підтверджено, що використання `TIMESTAMPTZ` забезпечує фізичне збереження даних в єдиному стандарті UTC, унеможливлюючи конфлікти часових зміщень у розподілених застосунках. За допомогою оператора `AT TIME ZONE` реалізовано динамічну конвертацію моменту створення замовлень у часові пояси Києва (+03) та Токіо (+09).
5. **Реалізовано динамічну аналітику на базі `generate_series()`:** Побудовано неперервні календарні ряди дат, здійснено фільтрацію вихідних днів через `EXTRACT(ISODOW)` та сформовано звіт продажів на повний жовтень 2026 року без пропуску нульових днів завдяки поєднанню `LEFT JOIN` та агрегації `COUNT(o.id)`.
6. **Впроваджено декларативне обмеження станів через `ENUM`:** Створено користувацький перелічуваний тип `lab42.order_status`, що гарантує цілісність життєвого циклу замовлень на рівні ядра СУБД та забезпечує компактне 4-байтне внутрішнє збереження статусів.
