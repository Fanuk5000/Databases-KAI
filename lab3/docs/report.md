## 2. Теоретичні відомості та архітектурний аналіз

### 2.1. Уніфікована рольова модель (RBAC) у PostgreSQL

У більшості класичних реляційних СУБД концепції «користувач» (обліковий запис для автентифікації) та «група» (контейнер прав) розділені на рівні різних системних об'єктів. У PostgreSQL реалізовано уніфіковану модель: єдина сутність — **роль** (`ROLE`).

- Команда `CREATE USER` є синтаксичним синонімом для `CREATE ROLE ... LOGIN`.
- Атрибут `LOGIN` визначає, чи може роль встановлювати пряме клієнтське з'єднання з базою даних за допомогою пароля або інших методів автентифікації.
- Ролі з атрибутом `NOLOGIN` не можуть самостійно авторизуватися на сервері. Вони виконують роль груп або контейнерів привілеїв, до яких включаються інші ролі, або слугують цільовими контекстами для тимчасового перемикання сесії через `SET ROLE`.
- Атрибут `INHERIT` дозволяє ролі автоматично успадковувати всі привілеї групових ролей, до складу яких вона входить. При вимкненому успадкуванні (`NOINHERIT`) привілеї групи стають активними лише після явного виконання `SET ROLE <group_name>`.
- Починаючи з **PostgreSQL 16**, запроваджено розширений контроль членства: право застосовувати `SET ROLE` на іншу роль потребує явної видачі членства з модифікатором `WITH SET TRUE` (`GRANT target_role TO current_user WITH SET TRUE;`).

### 2.2. Дворівнева перевірка прав доступу

Організація даних у PostgreSQL передбачає логічне групування об'єктів за просторами імен — **схемами** (`SCHEMAS`). Будь-який запит до таблиці, розміщеної всередині користувацької схеми, підлягає двом незалежним ітераціям авторизації:

```text
+-------------------------------------------------------------+
| Клієнтський SQL-запит: SELECT * FROM lab_demo.students      |
+-------------------------------------------------------------+
                              |
                              v
                [ Рівень 1: Перевірка схеми ]
          Чи має current_user право USAGE ON SCHEMA?
                 /                         \
             [HI]                          [ТАК]
               v                              v
   ERROR: permission denied       [ Рівень 2: Перевірка таблиці ]
      for schema lab_demo       Чи має current_user право SELECT?
                                       /                     \
                                   [HI]                      [ТАК]
                                     v                          v
                         ERROR: permission denied          Успішне
                            for table students         повернення даних
```

1. **Рівень схеми (`USAGE ON SCHEMA`):** Дозвіл на перегляд об'єктів усередині схеми та розв'язання їхніх імен (трансляція назви таблиці у внутрішній ідентифікатор `OID`). Без цього привілею доступ блокується на рівні схеми, навіть якщо роль володіє необмеженими правами на саму таблицю.
2. **Рівень об'єкта (`SELECT`, `INSERT`, `UPDATE`, `DELETE`):** Дозвіл на виконання безпосередньої операції з даними в таблиці.

### 2.3. Власник об'єкта (`tableowner`) проти привілеїв `GRANT`

Роль, від імені якої виконується команда створення об'єкта (`CREATE TABLE`, `CREATE SCHEMA`), фіксується як його **власник** (`tableowner`).

- Власник автоматично наділений вичерпними привілеями над об'єктом, включаючи право модифікувати схему (`ALTER TABLE`), видаляти об'єкт (`DROP TABLE`), передавати права іншим ролям (`GRANT`) та налаштовувати політики безпеки на рівні рядків (RLS).
- Права, надані іншим ролям через команду `GRANT`, делегують лише повноваження маніпуляції даними (DML) і не надають адміністративних прав на зміну структури чи видалення об'єкта.

### 2.4. Перемикання контексту сесії: `current_user` проти `session_user`

- `session_user` — ідентифікатор користувача, під яким було встановлено первинне TCP/сокет-підключення до СУБД. Це значення залишається незмінним протягом усього життєвого циклу клієнтського сеансу.
- `current_user` — роль, від імені якої ядро СУБД виконує поточну перевірку прав доступу на кожен запит.
- Команда `SET ROLE <role_name>` змінює значення `current_user` у межах поточної сесії. Це дає змогу адміністраторам та розробникам тестувати обмеження безпеки різних ролей без потреби створювати окремі підключення чи відкривати нові сеанси.
- Команда `RESET ROLE` повертає значення `current_user` до значення первинного `session_user` (`postgres`).

```text
+------------------------------------------------------------------------+
| Сеанс підключення: session_user = postgres                             |
|                                                                        |
|  [За замовчуванням]        SET ROLE lab_reader        RESET ROLE       |
|  current_user = postgres  -------------------->   current_user =       |
|  (Повні права власника)                             lab_reader         |
|                                                   (Обмежені права)     |
+------------------------------------------------------------------------+
```

### 2.5. Шлях пошуку об'єктів (`search_path`) та вразливості схеми `public`

Змінна сесії `search_path` містить список схем у порядку спадання їхнього пріоритету перегляду:

- При виконанні запиту з коротким іменем (`SELECT * FROM students;`) сервер перебирає схеми зі списку `search_path` зліва направо і звертається до першої таблиці з відповідним іменем.
- Якщо таблиця `students` одночасно існує в схемах `public` і `lab_demo`, запит із коротким іменем може звернутися не до цільової таблиці, якщо порядок схем у `search_path` зміниться.
- **Вразливість підміни об'єктів (Schema Shadowing):** Якщо сторонньому користувачеві надано право створення об'єктів у спільній схемі `public`, він може створити таблицю або функцію з тим самим іменем, що й системний об'єкт. Якщо `public` розташована на початку шляху пошуку, застосунок виконає звернення до підробленого об'єкта. Використання повністю кваліфікованих імен (`lab_demo.students`) усуває цю вразливість.

### 2.6. Конфігурація сеансу, сервера та представлення `pg_settings`

Параметри СУБД PostgreSQL розділені на рівні застосування, що визначаються полем `context` у системному каталозі `pg_settings`:

- `user`: параметри, які кожен користувач може вільно змінювати для своєї поточної сесії через команду `SET` (наприклад, `statement_timeout`, `search_path`, `timezone`). Зміни діють негайно і скидаються після закриття з'єднання.
- `superuser`: параметри сеансу, які дозволено змінювати лише суперкористувачеві.
- `sighup`: параметри сервера, зміна яких потребує перечитування конфігураційних файлів без зупинки процесу СУБД (надсилання сигналу `SIGHUP` або виконання `SELECT pg_reload_conf()`).
- `postmaster`: глобальні параметри виділення системних ресурсів (наприклад, `max_connections`, `shared_buffers`), зміна яких вимагає повного перезапуску демона PostgreSQL.
- `internal`: незмінні параметри, визначені під час збирання виконуваних файлів або ініціалізації кластера (`initdb`).

### 2.7. Автоматичні привілеї майбутніх об'єктів (`ALTER DEFAULT PRIVILEGES`)

Стандартний механізм `GRANT` діє виключно за фактом: права надаються тільки на ті таблиці чи схеми, які вже існують у момент виконання команди.

- Якщо роль-власник створює нову таблицю після налаштування прав, сторонні ролі автоматично не отримують до неї доступу.
- Директива `ALTER DEFAULT PRIVILEGES FOR ROLE <creator> IN SCHEMA <schema> GRANT ... ON TABLES TO <target_role>` формує декларативне правило для ядра СУБД: будь-яка таблиця, яку в майбутньому створить роль `<creator>` у вказаній схемі, автоматично отримає визначений набір привілеїв для ролі `<target_role>`.

### 2.8. Серверні файли конфігурації: `postgresql.conf` та `pg_hba.conf`

- **`postgresql.conf`:** Основний конфігураційний файл ядра СУБД. Містить параметри керування пам'яттю (`shared_buffers`, `work_mem`), мережеві інтерфейси (`listen_addresses`, `port`), налаштування транзакційного журналу WAL, поведінку підсистеми журналювання та автоочищення (`autovacuum`).
- **`pg_hba.conf` (Host-Based Authentication):** Керує безпекою на мережевому транспортному рівні. Визначає правила допуску клієнтів:

  ```text
  # TYPE  DATABASE  USER     ADDRESS          METHOD
  host    all       user1    192.168.1.0/24   scram-sha-256
  host    all       all      0.0.0.0/0        reject
  ```

  Правила перевіряються строго зверху вниз до першого збігу. Якщо клієнт задовольняє першому рядку, запитується пароль за алгоритмом SCRAM-SHA-256; для решти підключень спрацьовує правило `reject`.
- **Специфіка хмари Supabase:** Обидва файли адмініструються хмарною платформою автоматично для забезпечення високої доступності та ізоляції контейнерів. Користувачі керують базою через клієнтські підключення та SQL Editor.

## 3. Протокол виконання та аналіз фактичних логів сесії

Усі наведені нижче фрагменти SQL-команд та виводу сервера зафіксовані під час виконання практичних завдань у хмарній базі даних Supabase (файл протоколу `savings.txt`).

### 3.1. Перевірка підключення та системних просторів імен

Перед початком конфігурації перевірено поточні атрибути сеансу:

```text
postgres=> SELECT 
current_database()
current_user,
session_user;
 current_user | session_user 
--------------+--------------
 postgres     | postgres
(1 row)
```

Перевірка переліку зареєстрованих схем у базі даних Supabase за допомогою клієнтської команди `\dn`:

```text
postgres=> \dn
          List of schemas
      Name      |       Owner       
----------------+-------------------
 auth           | supabase_admin
 extensions     | postgres
 graphql        | supabase_admin
 graphql_public | supabase_admin
 lab_demo       | postgres
 pgbouncer      | pgbouncer
 public         | pg_database_owner
 realtime       | supabase_admin
 storage        | supabase_admin
 vault          | supabase_admin
(10 rows)
```

**Аналіз архітектури схем Supabase:**

- `lab_demo`: створена нами ізольована схема під керуванням ролі `postgres`.
- `auth`, `storage`, `vault`, `realtime`: внутрішні системні схеми платформи Supabase, що ізолюють дані автентифікації користувачів додатка, файлових сховищ, ключів шифрування та веб-сокетів. Їхнім власником є суперсервісна роль `supabase_admin`.
- `pgbouncer`: службова схема пулера підключень.
- `extensions`: схема для реєстрації розширень PostgreSQL (наприклад, `uuid-ossp`, `pgcrypto`).
- `public`: стандартна загальна схема бази даних.

### 3.2. Створення схеми, таблиці та початкове наповнення даними

У схемі `lab_demo` створено таблицю `students` та додано тестові записи студентів:

```text
postgres=> SELECT * FROM lab_demo.students ORDER BY id;
 id |  name   | group_name | rating 
----+---------+------------+--------
  1 | Illia   | B-121      |    100
  2 | Maksym  | B-123      |    100
  3 | Natasha | -121       |     95
(3 rows)
```

Виявлено механічну помилку в назві академічної групи третього запису (`'-121'` замість `'B-121'`). Помилку виправлено за допомогою оператора `UPDATE`:

```text
postgres=> UPDATE lab_demo.students SET group_name='B-121' where id=3;
UPDATE 1

postgres=> SELECT * FROM lab_demo.students ORDER BY id;
 id |  name   | group_name | rating 
----+---------+------------+--------
  1 | Illia   | B-121      |    100
  2 | Maksym  | B-123      |    100
  3 | Natasha | B-121      |     95
(3 rows)
```

### 3.3. Інспекція власника таблиці у системному каталозі

Виконано запит до системного каталогу `pg_tables` для підтвердження прав володіння об'єктом:

```text
postgres=> SELECT schemaname, tablename, tableowner
postgres-> FROM pg_tables
postgres-> WHERE schemaname = 'lab_demo';
 schemaname | tablename | tableowner 
------------+-----------+------------
 lab_demo   | students  | postgres
(1 row)
```

*Результат:* Таблиця належить ролі `postgres`, яка має повні повноваження власника (DDL/DCL). Інші ролі наразі позбавлені доступу.

### 3.4. Створення ролей та налаштування прав

Створено ролі `lab_reader` та `lab_editor` з параметром `NOLOGIN`, адміністратору `postgres` надано членство з правом перемикання (`WITH SET TRUE`), після чого призначено матрицю привілеїв:

- `GRANT USAGE ON SCHEMA lab_demo TO lab_reader, lab_editor;`
- `GRANT SELECT ON lab_demo.students TO lab_reader;`
- `GRANT SELECT, INSERT, UPDATE, DELETE ON lab_demo.students TO lab_editor;`

### 3.5. Верифікація повноважень читача (`lab_reader`)

Виконано перемикання на роль читача та перевірено операцію вибірки даних:

```text
postgres=> SET ROLE lab_reader;

SELECT
    current_user,
    id,
    name,
    group_name,
    rating
FROM lab_demo.students
ORDER BY id;

RESET ROLE;
SET
 current_user | id |  name   | group_name | rating 
--------------+----+---------+------------+--------
 lab_reader   |  1 | Illia   | B-121      |    100
 lab_reader   |  2 | Maksym  | B-123      |    100
 lab_reader   |  3 | Natasha | B-121      |     95
(3 rows)
```

Перевірка негативного сценарію — спроба змінити рейтинг студента під роллю читача:

```text
postgres=> SET ROLE lab_reader;

UPDATE lab_demo.students
SET rating = 60 
WHERE id = 1;
SET
ERROR:  permission denied for table students
```

*Результат:* Операція `SELECT` виконана успішно (`current_user = lab_reader`). Спроба модифікації даних заблокована ядром СУБД з системною помилкою `permission denied for table students`, що підтверджує надійність ізоляції ролі.

### 3.6. Верифікація повноважень редактора (`lab_editor`)

Під роллю `lab_editor` послідовно виконано операції додавання, оновлення та видалення запису з миттєвим поверненням результатів через вираз `RETURNING *`:

**1. Додавання нового запису (INSERT):**

```text
postgres=> SET ROLE lab_editor;

INSERT INTO lab_demo.students (id, name, group_name, rating)
VALUES (4, 'Дмитро', 'B-121', 80)
RETURNING *;

RESET ROLE;
SET
 id |  name  | group_name | rating 
----+--------+------------+--------
  4 | Дмитро | B-121      |     80
(1 row)

INSERT 0 1
RESET
```

**2. Модифікація запису (UPDATE):**

```text
postgres=> SET ROLE lab_editor;

UPDATE lab_demo.students
SET rating = 90
WHERE id = 4
RETURNING *;

RESET ROLE;
SET
 id |  name  | group_name | rating 
----+--------+------------+--------
  4 | Дмитро | B-121      |     90
(1 row)

UPDATE 1
RESET
```

**3. Видалення тестового запису (DELETE):**

```text
postgres=> SET ROLE lab_editor;

DELETE FROM lab_demo.students
WHERE id = 4
RETURNING *;

RESET ROLE;
SET
 id |  name  | group_name | rating 
----+--------+------------+--------
  4 | Дмитро | B-121      |     90
(1 row)

DELETE 1
RESET
```

*Результат:* Роль `lab_editor` успішно виконала весь життєвий цикл маніпуляції даними (DML). Вираз `RETURNING *` дозволив відстежити стан рядка без окремого запиту `SELECT`.

### 3.7. Точкове відкликання привілеїв (`REVOKE`)

Адміністратор виконав точкове відкликання права на оновлення у ролі редактора:
`REVOKE UPDATE ON lab_demo.students FROM lab_editor;`

Перевірка заборони операції оновлення під роллю `lab_editor`:

```text
postgres=> SET ROLE lab_editor;

UPDATE lab_demo.students
SET rating = 1  
WHERE id = 1;
SET
ERROR:  permission denied for table students
```

Перевірка збереження привілею на читання:

```text
postgres=> RESET ROLE;

SET ROLE lab_editor;

SELECT *
FROM lab_demo.students
ORDER BY id;

RESET ROLE;
RESET
SET
 id |  name   | group_name | rating 
----+---------+------------+--------
  1 | Illia   | B-121      |    100
  2 | Maksym  | B-123      |    100
  3 | Natasha | B-121      |     95
(3 rows)

RESET
```

*Результат:* Команда `REVOKE` діє строго вибірково: право `UPDATE` анульовано, проте право `SELECT` збереглося в повному обсязі.

### 3.8. Дослідження групової ролі та успадкування (`INHERIT`)

Створено роль `lab_member` без права входу, але з активним успадкуванням (`NOLOGIN INHERIT`), яку включено до складу групи `lab_reader`:

- `CREATE ROLE lab_member NOLOGIN INHERIT;`
- `GRANT lab_reader TO lab_member;`
- `GRANT lab_member TO postgres WITH SET TRUE;`

Перевірка читання через успадковане членство:

```text
postgres=> SET ROLE lab_member;

SELECT
    current_user,
    id,
    name,
    group_name
FROM lab_demo.students
ORDER BY id;

RESET ROLE;
SET
 current_user | id |  name   | group_name 
--------------+----+---------+------------
 lab_member   |  1 | Illia   | B-121
 lab_member   |  2 | Maksym  | B-123
 lab_member   |  3 | Natasha | B-121
(3 rows)

RESET
```

Відкликання членства в групі (`REVOKE lab_reader FROM lab_member;`) та повторна перевірка:

```text
postgres=> SET ROLE lab_member;

SELECT *
FROM lab_demo.students;
SET
ERROR:  permission denied for schema lab_demo
LINE 2: FROM lab_demo.students;
```

*Результат:* Роль `lab_member` спочатку успішно зчитала дані завдяки автоматичному успадкуванню прав групи `lab_reader`. Після відкликання членства роль миттєво втратила доступ і отримала помилку `permission denied for schema lab_demo`. Це доводить ключову перевагу RBAC: керування доступом співробітників здійснюється однією дією зміни членства в групі.

### 3.9. Інспекція атрибутів ролей у `pg_roles`

Виконано опитування системного каталогу `pg_roles` для перевірки параметрів безпеки:

```text
postgres=> SELECT rolname, rolcanlogin, rolsuper, rolcreatedb, rolcreaterole, rolinherit FROM pg_roles WHERE rolname IN ('postgres', 'lab_reader', 'lab_editor', 'lab_member') ORDER BY rolname;
  rolname   | rolcanlogin | rolsuper | rolcreatedb | rolcreaterole | rolinherit 
------------+-------------+----------+-------------+---------------+------------
 lab_editor | f           | f        | f           | f             | t
 lab_member | f           | f        | f           | f             | t
 lab_reader | f           | f        | f           | f             | t
 postgres   | t           | f        | t           | t             | t
(4 rows)
```

**Аналіз атрибутів:**

- `rolcanlogin`: значення `true` (`t`) встановлено лише для `postgres`. Навчальні ролі мають `false` (`f`), що виключає ризик несанкціонованого прямого входу.
- `rolsuper`: у хмарному середовищі Supabase користувач `postgres` має `false` (`f`), оскільки повні привілеї суперкористувача зарезервовані за внутрішньою роллю платформи `supabase_admin`.
- `rolcreatedb` / `rolcreaterole`: роль `postgres` наділена правами створення нових баз даних та керування ролями.
- `rolinherit`: усі ролі мають активний прапорець успадкування (`t`).

### 3.12. Аналіз контекстів параметрів у `pg_settings`

Виконано запит для зіставлення параметрів різного рівня впливу:

```text
postgres=> SELECT name, setting, unit, context, pending_restart FROM pg_settings WHERE name IN ('statement_timeout', 'max_connections');
       name        | setting | unit |  context   | pending_restart 
-------------------+---------+------+------------+-----------------
 max_connections   | 60      |      | postmaster | f
 statement_timeout | 120000  | ms   | user       | f
(2 rows)
```

**Порівняльний аналіз:**

- `statement_timeout`: значення `120000 ms`, `context = user`. Може вільно переналаштовуватися клієнтом у сеансі через `SET`.
- `max_connections`: значення `60`, `context = postmaster`. Визначає максимальний пул підключень на рівні операційної системи. Його зміна можлива лише через конфігурацію сервера і вимагає повного перезапуску демона PostgreSQL (`pending_restart = f` підтверджує, що очікування перезапуску наразі немає).

### 3.13. Автоматичні привілеї майбутніх об'єктів (`ALTER DEFAULT PRIVILEGES`)

Налаштовано правило за замовчуванням для майбутніх таблиць, які створюватимуться користувачем `postgres`:

```sql
ALTER DEFAULT PRIVILEGES
FOR ROLE postgres
IN SCHEMA lab_demo
GRANT SELECT ON TABLES TO lab_reader;
```

Створено нову таблицю `notes` та додано запис:

```sql
CREATE TABLE lab_demo.notes (message TEXT);
INSERT INTO lab_demo.notes VALUES ('Навчальна нотатка');
```

Перевірка читання роллю `lab_reader` без виконання явного `GRANT` на таблицю `notes`:

```text
postgres=> SET ROLE lab_reader;

SELECT *
FROM lab_demo.notes;

RESET ROLE;
SET
      message      
-------------------
 Навчальна нотатка
(1 row)

RESET
```

*Результат:* Запит виконано успішно. Директива `ALTER DEFAULT PRIVILEGES` позбавляє потреби вручну роздавати права на кожен новий об'єкт після релізу міграцій.

## 4. Відповіді на контрольні питання

### 1. Для чого використовується команда `GRANT`?

**Відповідь:** Команда `GRANT` призначена для делегування привілеїв доступу (наприклад, `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `USAGE`, `CREATE`) на об'єкти бази даних (таблиці, схеми, послідовності, функції) певним ролям, або для надання ролям членства в інших ролях.

### 2. Чим `REVOKE` відрізняється від `GRANT`?

**Відповідь:** `REVOKE` є синтаксично та функціонально протилежною операцією, яка відкликає раніше надані привілеї або вилучає роль зі складу іншої ролі. Команда діє строго точково на перелічений набір прав, залишаючи решту привілеїв незмінними.

### 3. Для чого потрібне право `USAGE` на схему і чому недостатньо лише `SELECT` на таблицю?

**Відповідь:** Схема є логічним контейнером простору імен. Право `USAGE` санкціонує доступ до самої схеми та дозволяє трансляцію імен внутрішніх об'єктів в їхні системні OID. Якщо `USAGE` відсутнє, сервер блокує запит на етапі пошуку об'єкта у просторі імен з помилкою `permission denied for schema`, навіть якщо на саму таблицю роль має повні права `SELECT`.

### 4. Що робить команда `SET ROLE` і в яких межах вона діє?

**Відповідь:** `SET ROLE` тимчасово замінює значення змінної `current_user` на вказану роль. Усі наступні команди в сеансі виконуються від імені цієї ролі та проходять відповідні перевірки прав. Дія команди обмежується рамками поточного з'єднання (сесії) або активної транзакції (при `SET LOCAL ROLE`).

### 5. Що робить команда `RESET ROLE`?

**Відповідь:** Команда скидає тимчасовий контекст і повертає значення `current_user` до вихідної ролі автентифікації сесії — значення `session_user` (`postgres`).

### 6. Чим `current_user` відрізняється від `session_user`?

**Відповідь:** `session_user` — це обліковий запис, під яким було ініційовано підключення клієнта до СУБД; він залишається постійним протягом усього часу з'єднання. `current_user` — це активна роль, чиї права ядро перевіряє в даний момент. При виконанні `SET ROLE` змінюється лише `current_user`.

### 7. Для чого потрібен параметр `search_path`?

**Відповідь:** Визначає послідовність перегляду схем сервером PostgreSQL під час розв'язання некваліфікованих імен таблиць, представлень чи функцій.

### 8. Чим повне ім'я `lab_demo.students` краще за коротке `students`?

**Відповідь:** Кваліфіковане ім'я виду `schema.table` є детермінованим: воно однозначно адресує об'єкт незалежно від конфігурації `search_path` клієнта і захищає систему від вразливості підміни об'єктів (Schema Hijacking / Shadowing).

### 9. Що означає атрибут `NOLOGIN` і навіщо він у навчальних ролях?

**Відповідь:** Атрибут `NOLOGIN` забороняє встановлювати пряме клієнтське з'єднання з базою даних від імені цієї ролі. У навчальних цілях це запобігає відкриттю нових незахищених точок входу до СУБД і дозволяє тестувати права через перемикання контексту `SET ROLE` в межах наявного сеансу адміністратора.

### 10. Що означає атрибут `INHERIT` і як поводиться роль із `NOINHERIT`?

**Відповідь:** `INHERIT` вмикає автоматичне успадкування роллю всіх прав тих груп, членом яких вона є. При `NOINHERIT` членство в групі зберігається, проте привілеї групи стають доступними лише після явного виконання оператора `SET ROLE <group_role>`.

### 11. Для чого потрібна команда `ALTER DEFAULT PRIVILEGES` і на які об'єкти вона не впливає?

**Відповідь:** Призначена для визначення прав доступу, які автоматично призначатимуться об'єктам, що будуть створені вказаною роллю в майбутньому. Вона **не впливає** на вже наявні об'єкти на момент її запуску (для них необхідний явний `GRANT`), а також на об'єкти, створені іншими користувачами, якщо вони не зазначені у блоці `FOR ROLE`.

### 12. Які параметри можна змінити в поточному сеансі, а які — ні?

**Відповідь:** У поточному сеансі через `SET` можна змінювати параметри з контекстом `user` (а також `superuser`, якщо поточний користувач володіє правами суперкористувача). Параметри з контекстами `sighup`, `postmaster` та `internal` змінити через `SET` неможливо.

### 13. Що означає `context = postmaster` у представленні `pg_settings`?

**Відповідь:** Це означає, що параметр може бути встановлений виключно у файлі конфігурації сервера або переданий як аргумент командного рядка під час запуску демона, і набуває чинності лише після повного перезапуску процесу PostgreSQL.

### 14. Для чого призначений файл `postgresql.conf`?

**Відповідь:** Головний конфігураційний файл СУБД PostgreSQL. Керує глобальними налаштуваннями сервера: виділенням оперативної пам'яті (`shared_buffers`, `work_mem`), лімітами пулів з'єднань, адресами прослуховування, політиками контрольних точок (checkpoints) та журналуванням помилок.

### 15. Для чого призначений файл `pg_hba.conf` і в якому порядку перевіряються його правила?

**Відповідь:** Визначає правила клієнтської автентифікації на мережевому рівні хоста. Записи фільтрують підключення за типом (`local`/`host`), цільовою базою, користувачем, IP-підмережею та методом шифрування/перевірки пароля. Записи аналізуються послідовно зверху вниз до першого збігу параметрів.

### 16. Які повноваження має власник таблиці порівняно з роллю, якій надано права через `GRANT`?

**Відповідь:** Власник володіє повним спектром DDL-прав над об'єктом: має право виконувати `ALTER TABLE`, додавати стовпці та індекси, встановлювати обмеження цілісності, видаляти таблицю (`DROP TABLE`), налаштовувати RLS та роздавати привілеї іншим користувачам. Роль із привілеями через `GRANT` обмежена виключно дозволеними DML операціями (`SELECT`, `INSERT`, `UPDATE`, `DELETE`) і не може впливати на структуру таблиці.

## 5. Завдання для самоперевірки

### 1. Чим відрізняється знак `=` у `SET rating = 90` та `WHERE id = 4`?

- У виразі `SET rating = 90` оператор `=` виконує операцію **присвоєння** нового значення атрибуту стовпця (частина синтаксису DML команди `UPDATE`).
- У виразі `WHERE id = 4` оператор `=` є логічним оператором **порівняння**, який обчислює булевий предикат (`TRUE`/`FALSE`/`UNKNOWN`) для фільтрації рядків відношення.

### 2. Що означає кожна частина імені `lab_demo.students`? Чи надає це ім'я право читання?

- `lab_demo` — ім'я схеми (простору імен); `students` — ім'я реляційної таблиці всередині зазначеної схеми.
- Запис кваліфікованого імені є суто адресацією і автоматично не надає жодних прав. Для читання роль обов'язково повинна володіти привілеями `USAGE` на схему `lab_demo` та `SELECT` на таблицю `students`.

### 3. Чому `'Анна'` записано в одинарних лапках, а число `85` — без них?

- В одинарних лапках (`'...'`) за стандартом SQL записуються строкові константи (літерали типів `TEXT`, `VARCHAR`).
- Числа записуються без лапок як числові константи (`INTEGER`, `NUMERIC`). Подвійні лапки (`"..."`) у PostgreSQL зарезервовані для ідентифікаторів об'єктів (наприклад, назв таблиць або стовпців із регістрозалежними чи спеціальними символами).

### 4. Що зміниться після `SET ROLE lab_reader`: база даних, `current_user` чи `session_user`?

- Зміниться виключно змінна **`current_user`** (отримає значення `lab_reader`). Назва бази даних і значення `session_user` (залишається `postgres`) залишаються незмінними.

### 5. Чому для читання таблиці потрібні і `USAGE` на схему, і `SELECT` на таблицю?

- Схема ізолює простір імен: без привілею `USAGE` сервер відмовляє в трансляції імені об'єкта в `OID`. Дозвіл `SELECT` регулює доступ безпосередньо до кортежів даних. Перевірка доступу є послідовною: без подолання першого бар'єру (схеми) перевірка прав на таблицю не здійснюється.

### 6. Чим відрізняються `GRANT SELECT ON lab_demo.students TO lab_reader` та `GRANT lab_reader TO lab_member`?

- Перша команда надає привілей на рівні об'єкта: право виконувати запити вибірки даних із таблиці.
- Друга команда надає членство в іншій ролі: робить `lab_member` учасником ролі `lab_reader`, дозволяючи їй успадковувати всі права, закріплені за роллю `lab_reader`.

### 7. Практична вправа: вивести `name` і `rating` студентів групи A за спаданням рейтингу

```sql
SELECT name, rating
FROM lab_demo.students
WHERE group_name = 'A'
ORDER BY rating DESC;
```

### 8. Практична вправа: перевірити читання під роллю `lab_reader` та повернутися до початкової ролі

```sql
SET ROLE lab_reader;
SELECT * FROM lab_demo.students;
RESET ROLE;
```

### 9. Практична вправа: скласти команду, яка відкликає тільки право `DELETE` у `lab_editor`

```sql
REVOKE DELETE ON lab_demo.students FROM lab_editor;
```

## 6. Висновки

1. **Опановано рольову модель доступу RBAC у PostgreSQL:** Досліджено специфіку єдиної сутності `ROLE`, яка замінює застаріле розділення на користувачів і групи. На практиці створено ролі з властивостями `NOLOGIN` (`lab_reader`, `lab_editor`, `lab_member`) та досліджено сумісність директиви `WITH SET TRUE` у PostgreSQL 16+ для хмарного середовища Supabase.
2. **Підтверджено дворівневу архітектуру перевірки привілеїв:** Експериментально доведено, що наявність привілею на читання таблиці (`SELECT`) без права використання схеми (`USAGE ON SCHEMA`) призводить до блокування операції на рівні схеми з системною помилкою `permission denied for schema`.
3. **Досліджено перемикання контексту сесії:** За допомогою команд `SET ROLE` і `RESET ROLE` продемонстровано можливість повноцінного тестування ізоляції прав без необхідності відкриття нових клієнтських підключень. Зафіксовано різницю між змінними `current_user` (активний контекст прав) та `session_user` (первинний користувач автентифікації `postgres`).
4. **Проведено позитивне та негативне тестування прав:**
   - Для ролі читача `lab_reader` підтверджено успішне виконання `SELECT` та гарантоване блокування спроби модифікації даних з помилкою `permission denied for table students`.
   - Для ролі редактора `lab_editor` підтверджено коректне виконання операцій повного циклу DML (`INSERT`, `UPDATE`, `DELETE`) з використанням зворотної проекції `RETURNING *`.
5. **Підтверджено точкову дію команди `REVOKE`:** Доведено, що скасування окремого привілею (`REVOKE UPDATE`) надійно блокує спроби редагування, зберігаючи при цьому інші призначені права (`SELECT`).
6. **Досліджено механізм групового успадкування (`INHERIT`):** На прикладі ролі `lab_member` продемонстровано автоматичне отримання прав через членство в ролі `lab_reader` та миттєве блокування доступу після вилучення з групи без потреби індивідуального перегляду привілеїв таблиць.
7. **Проаналізовано керування простором імен через `search_path`:** Практично доведено зручність коротких імен при модифікації шляху пошуку, але обґрунтовано безальтернативність кваліфікованих імен виду `lab_demo.students` для усунення атак типу Schema Shadowing.
8. **Досліджено контексти параметрів у системному каталозі `pg_settings`:** Визначено відмінність між сеансовими параметрами (`statement_timeout`, `context = user`), які безпечно змінюються командами `SET` / `RESET`, та критичними ресурсомісткими параметрами ядра (`max_connections`, `context = postmaster`), що вимагають повного перезапуску екземпляра СУБД.
9. **Застосовано автоматичні привілеї майбутніх об'єктів:** Завдяки команді `ALTER DEFAULT PRIVILEGES` підтверджено успішне автоматичне делегування прав читання на нову таблицю `lab_demo.notes` ролі `lab_reader` без необхідності ручного втручання адміністратора після створення таблиці.
